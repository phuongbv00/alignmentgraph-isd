## The `alignmentgraph-isd` package (thesis core)

Located in `alignmentgraph-isd/src/alignmentgraph_isd/`. **The full pipeline is the default and only preset** (the former `HARNESS_ABLATION` preset system was removed in the 2026-07 RQ pivot; do not reintroduce it). For the defense ablation study, `HarnessRunConfig` carries exactly two axes, defaults = the full pipeline: `agent_mode` (`"multi"` | `"single"` — decomposition; `single` runs `SingleDesignerAgent`, one persona over the same steps) and `context_mode` (`"graph"` | `"prose"` — the alignment machinery **as a bundle**: `"prose"` runs a graph-free `ProseStore` blackboard (`core/prose_store.py`) where each step deposits its whole parsed JSON under one document key and later steps read documents back verbatim by a static read-list; safeguards reduce to the 6 within-artifact checks + shared self-repair/regen (and note two of the six families — activity, content — carry ONLY cross-artifact checks, so in prose they get no self-validation and no repair at all); no docket, no audit, and NO `graph`/`graph_dot` result keys — instead `result["prose"]` carries the raw blackboard dump, saved as `<agent_id>_prose.json` (inspection artifact, not an audit). Never implement prose as a renderer/adapter over the graph — that was the retired 2026-08 design and it made the axis measure surface form only). Axes are set solely via the benchmark's per-arm agent registrations (`alignmentgraph-isd-single-prose`, `-single-graph`, `-multi-prose` in `run_benchmark.py`), and the resolved axes are recorded in `metadata.run_config`.

Public API (see the package README for details):

```python
from alignmentgraph_isd import DesignBrief, HarnessRunConfig, run_design_brief
result = run_design_brief(brief, config)   # config.llm_factory is REQUIRED — hard error, never silent empty output
# result keys: addie_output, trajectory, metadata, graph, graph_dot
```

Layout:

- **`config.py`** — `HarnessRunConfig`: `llm_factory` (any LangChain chat-model factory, required), `use_rag` + `retrieval_subagents` (RAG gate, both required to open it), `regen_budget`/`regen_backoff_seconds` (re-run a specialist whose section came back with empty required fields; the benchmark adapter sources these from `BENCHMARK_DELAY` / `HARNESS_REGEN_*` env), `llm_max_concurrency`/`llm_min_interval_seconds` (the outbound-call gate, `core/ratelimit.py`). **The multi arm's `content_designer` and `rubric_designer` share a superstep and each fans out one Developer call per work set, so one agent peaks at ~12 concurrent LLM requests (measured on the test fixture) while the benchmark's `-r` posture counted it as ONE unit** — a shared endpoint answered the overflow with HTTP 429 on the two multi arms (9–25 per run over three runs) and 0–2 on the sequential single arms, putting a throttling handicap on the `agent_mode` ablation axis itself. The gate is per-run, never process-wide (a shared one would make one arm queue behind another and inflate its `execution_time_seconds`). Default 0 = unbounded standalone; `run_benchmark.py` stays free of any agent's internal knobs — it publishes only its own posture (`BENCHMARK_RATE_LIMIT` + `BENCHMARK_DELAY`), and the adapter owns the mapping (`LLM_CONCURRENCY_BY_RATE_LIMIT`: conservative 2 / moderate 3 / aggressive 4 / turbo 6, else 4), overridable with `HARNESS_LLM_MAX_CONCURRENCY` (0 opts out). `llm_min_interval_seconds` is off by default and deliberately NOT wired to `BENCHMARK_DELAY` — that is a between-agents delay, not a per-call one.
- **`cli.py`** — `alignmentgraph-isd run` on a JSON file already in `DesignBrief` shape; builds a model from `--model-*` flags or `AGENT_MODEL_*` env vars.
- **`core/runner.py`** — `MetaAgent`: builds and invokes the compiled LangGraph `StateGraph` per design brief, packages output + trajectory + graph dump.
- **`core/alignment_graph/`** — the AlignmentGraph subsystem as a package (since 2026-08-26; exactly the bundle the `context_mode` axis ablates — a prose run USES nothing from it; `NodeType` is imported module-level as an artifact-family key, but every real graph call is gated on `context_mode` and a prose run holds `graph = None`): `graph.py` holds `AlignmentGraph`/`NodeType`, `alignment.py` the relation registry + establishers, `audit.py` the `GraphAuditor` residual audit, `viz.py` the node-link/DOT dumps; `AlignmentGraph`/`NodeType` are re-exported at the package root. `AlignmentGraph` is the alignment-dependency graph of ISD artifacts. Edge type = human-readable relation key in `"<id>-<verb>"` form (e.g. `"C2-assessed_by"`, `"P10-delivers"`); **18 relations total: 7 core (`C1`–`C7`) + 11 secondary (`P1`–`P11`)**, defined once in `core/alignment_graph/alignment.py::REGISTRY`. Core relations are the construct-validity backbone and each carries a `theory` citation (Constructive Alignment / Backward Design / outcome-based assessment); secondary relations are provenance and traceability only, and are never claimed as construct-validity evidence. Every ELEMENT node must be reachable by some relation — SECTION nodes are singleton documents or narrative residues ONLY (2026-08-27: the legacy full-list sections objective_0/activity_0 were retired and assessment_0 removed outright; element nodes are the single source of truth for every item list, and repairs read/write elements directly). Narrative sections (gap_0/topic_0/constraint_0/improvement_0) connect to their elements via structural `narrates` edges (non-registry, the `precedes` class: dump/DOT/webapp navigation for the human auditor; never read by docket, checks or coverage). `development.expert_review` is ALWAYS synthesized by the aggregator from the verification that actually ran (self-validation rounds + repairs + relation coverage; prose arm: rounds/repairs only) — the model-authored review was removed from every generation schema 2026-08-27 (a same-model same-call review of artifacts that don't exist yet is fiction, and collided with the separate REAL expert-validation package). `to_full_dict()` / `to_dot()` produce the per-run graph dump (saved as `<agent_id>_graph.json` / `.dot` in benchmark results) — this is the auditability contribution. Prose-arm runs build no graph and ship no dump — that absence is the reported auditability contrast.
- **`core/agents/`** — specialist agents, one per ISD concern (`needs_context`, `objective_design`, `assessment_design`, `activity_material`, `implementation_plan`, `evaluation_revision`), plus `pedagogical_verifier` (content-level alignment checks + LLM repair) and `addie_aggregator` (assembles final ADDIE output). All extend `core/agents/base.py` (`BaseISDAgent`).
- **`core/rag/`** — external-corpus retrieval (`agent.py`, `planner.py`, `sandbox.py`).
- **`core/`** also holds `ratelimit.py` (the outbound-call gate, see `config.py` above), `workflow.py` (the LangGraph StateGraph layer — node factories, the dev-plan fan-out, `build_workflow`; renamed from `nodes.py` 2026-08-26 to stop reading as "alignment-graph nodes"), `prose_store.py` (`ProseStore`), `checks.py`, `rulebook.py`, `repairs.py`, `llm.py`, `trajectory.py`, `validation.py`, `brief.py` (the `DesignBrief` contract; renamed from `schema.py` 2026-08-26 — "schema" now unambiguously means the ADDIE output contract in `validation.py`). **Shared substrate rule (2026-08-26)**: `rulebook.py` (per-family generation SCHEMA/RULES) and `repairs.py` (repair toolbox + `OWNED_BY_FAMILY`) are the single sources both decomposition arms compose from — specialists build persona+schema+rules prompts from the rulebook, `SingleDesignerAgent` composes the same `RULES_*` blocks (via `rules_for(state)` for the `outcomes` state, by direct concatenation elsewhere) and NEVER imports a specialist module or instantiates a Designer class. **RULES parity is test-enforced; SCHEMA parity is NOT** — the single arm's per-state JSON exemplars are hand-written and are weaker than `rulebook.SCHEMA_*` in places (e.g. `_TASK_ASSESSMENT_ITEMS` shows one `performance_task` exemplar against `SCHEMA_ASSESSMENT_ITEMS`' three, omitting `multiple_choice` with `options`/`correct_answer`), which plausibly biases the `item_completeness` check against that arm. Closing this needs a SCHEMA-parity assertion alongside the existing RULES one in `tests/test_ablation_flags.py`. Repairs run via `repairs.repair(family, violations, ctx)` under the calling agent's own identity. **A repair that supplies a MISSING artifact regenerates it through the model** (`_llm_repair_items`, `repair_item_completeness`, `repair_formative_methods`, `repair_pilot_data_plan`), one persona-free batched call with a deterministic fallback so convergence holds; only field-level fixes are pure templates. Synthesising a missing assessment item deterministically copied the objective's own `statement` into the item's `question`, which the RQ2 `objective_assessment_similarity` signal read as near-perfect correspondence — and since these are cross-artifact repairs that only the graph arm runs, the artefact sat on the `context_mode` axis itself (fixed 2026-08-30). **The objective's Bloom level field is `level`, not `cognitive_process`** (renamed 2026-08-30): the evaluator's `extract_objectives` reads `level`, so under the old name `bloom_vs_declared_agreement` was `null` on every alignmentgraph arm and family B's sanity check never ran. Assessment items keep `required_cognitive_process` and activities `learner_cognitive_process`. The `bloom` check now also validates `level` against Bloom's six — an out-of-taxonomy value short-circuited the verb comparison and passed silently. **There is no cross-agent feedback routing in either arm**: the deterministic router and the three validate checkpoints were removed 2026-08-28, `Violation.target_designer` is a dead field, and no `route` trajectory action survives — never describe routing as part of the `context_mode` bundle. `tests/fixtures/golden_prompts.json` pins all 18 composed prompts byte-for-byte (ladder comparability) — a deliberate wording change means regenerating the fixture, never letting prompts drift. The single source of truth for the ADDIE output contract is `validation.py` (`_ADDIE_PHASE_FIELDS`/`_SECTION_FIELDS`); the former `schema/addie_output.json` + warning-only jsonschema pass duplicated a strictly weaker subset of it and was removed 2026-08-25.
- **`server/` + `webapp/`** — the **demo web app** (FastAPI + React/Vite/Cytoscape), added 2026-08-06. See `server/README.md`. It is **strictly optional and must stay that way**: its dependencies live in the `[server]` extra, `alignmentgraph_isd/__init__.py` never imports `.server`, and `cli.py` imports it lazily inside the `serve` subcommand. The benchmark installs this package plain, so FastAPI/uvicorn/SQLModel must never become hard dependencies — `tests/test_import_isolation.py` is the guard, and `99_audit_artifacts.py`-style discipline applies: if that test fails, the experiment environment is about to get polluted. Run it with `./run-app.sh` (or `alignmentgraph-isd serve`) — single process only, since live runs are in-process state, so there is deliberately no `--workers` flag. Configured by `AGISD_SERVER_*`. The model is chosen in the app's own Model settings dialog and stored in its database (`server/llm_settings.py`), falling back to the same `AGENT_MODEL_*` the CLI and benchmark use; the API key is stored in clear text in the local SQLite file and never returned to the browser. A model *name* alone yields a usable factory but not a usable model, so the app constructs the client up front in `/api/health` and before starting a run — without that a run starts, every specialist fails, and it "completes" in milliseconds with an empty graph under a `succeeded` label.

**Live progress (`on_event`).** `run_workflow` / `MetaAgent.run` / `run_design_brief` take an optional keyword-only `on_event(kind, payload)` consumer, wired through `TrajectoryLogger`. It is purely additive — with no consumer every emit is a no-op and the recorded trajectory is byte-for-byte what it was — and exists because the harness is synchronous and one run takes 4–7 minutes, so a UI has nothing to show otherwise. Beyond mirroring the recorded streams it emits `phase_started`/`phase_finished` (from `workflow.py`) and `llm_started`/`llm_finished` (from `agents/base.py`), which record nothing but are the only signal during the ~50 s a single model call takes, plus `graph_snapshot`. A consumer that raises is swallowed; `HarnessCancelled` (a `BaseException`) is the deliberate exception and is how the app stops a run. **A `graph_snapshot` payload must be consumed synchronously** — it aliases the live graph, which later phases keep mutating.

**RAG = external-corpus retrieval only, and it is on-demand.** `use_rag` is off by default and off on the benchmark. When enabled, retrieval is NOT performed upfront: each specialist decides mid-task whether/how to retrieve (`BaseISDAgent._maybe_retrieve` → decision call → `core/rag/sandbox.py` executes single/sequential/parallel plans over `core/rag/agent.py` retrieval agents). Graph-context retrieval (the AlignmentGraph subgraph) is core, always on, and is **not** called RAG.

## The benchmark (`isd-agent-benchmark/`)

`run_benchmark.py` is the orchestrator. Key facts that aren't obvious from the README:

- **Agents run in-process, not as subprocesses.** `_get_agent_runner(agent_id, llm_config)` imports each agent's Python class directly and returns a `run(scenario) -> dict` closure. The CLI interfaces documented in `shared/interfaces/agent_interface.md` exist but the benchmark does not use them. Agent `src/` paths are added to `sys.path` at the top of `run_benchmark.py`.
- **The evaluator IS run as a subprocess** (`isd-evaluator`), with stdout streamed to parse `__EVAL_PROGRESS__` markers.
- Each agent must return `{"addie_output": ..., "trajectory": ..., "metadata": ...}`. Output schemas live in `shared/schemas/*.json`. The metadata saved in `*_trajectory.json` carries uniform `token_usage` + `execution_time_seconds` for every agent. **Token accounting follows the `LLMConfig` object lineage**: `_get_agent_runner` opens one scope per run with `LLMConfig.new_token_scope()`, `copy_with()` re-shares the counter (as it does the credential/endpoint round-robin), and `run_benchmark` reads `resolved_llm_config._token_counter` after the runner returns. `copy_with()` used to hand out a FRESH counter and the runner leaned on that side effect, which silently required agents never to copy the config they were handed — all six baselines copy it in `__init__` to pin model/temperature, so every one of them reported `token_usage` 0 from 2026-08-29 until this was fixed 2026-08-31, while `alignmentgraph-isd` kept real numbers because its own copy sits behind an `if max_tokens is None` guard the uniform max_tokens never trips. `shared/tests/test_token_accounting_reaches_agents.py` constructs all seven agents and asserts each ends up on the run's counter; only `09/11_gen_*_tables.py` never read tokens, so no paper number was affected — `15_gen_facts_sheet.py` was.
- **`shared/llm`** is the single source of LLM configuration. Agents must NOT read provider env vars or instantiate `ChatOpenAI`/`ChatAnthropic` directly — call `create_chat_model(llm_config)` / `llm_config_from_env()`. `LLMConfig.api_spec` is the API *contract* (`openai_compatible`/`anthropic`), distinct from `provider` (a backend preset label). Add providers via config, not agent code.
- `shared/llm/factory.py` also implements the three serving-protection env flags used for the self-hosted ladder (uniform across all agents — fairness): `AGENT_MODEL_MAX_TOKENS_CAP` (ladder value **8192**), `AGENT_MODEL_STREAMING=1`, `AGENT_MODEL_DISABLE_THINKING=1`.
- Agent vs. judge models are configured **separately** (`AGENT_MODEL_*` vs `JUDGE_MODEL_*`) to avoid self-preference bias. Judge config supports comma-separated lists aligned across names/providers/URLs, with `|` grouping multiple credentials per judge.
- Agent env-quads for the self-hosted Qwen pods (`QWEN{08B,2B,4B,9B}_AGENT_MODEL_*`) live in a **marker-managed block at the end of `.env`**, written by `scripts/3_sync_runpod_pods_env.py` (read-only against the RunPod API). Never hand-edit that block.
- Results land in `results/<dataset>_benchmark_<model>_<run_tag>_<ts>/` (e.g. `test_90_benchmark_Qwen3.5-2B_r1_...`) or `results/single_<ts>/` for single scenarios. Both launchers take `RUN_TAGS` (comma/space-separated, run sequentially per slot).

### Evaluator (`evaluator/`)

`isd_evaluator` package. ADDIE rubric scoring: 33 Context-Matrix sub-steps → 13 consolidated items → 5 ADDIE phases (100 pts), plus BFCL-based trajectory scoring; per-scenario `total_score = 0.7·ADDIE + 0.3·Trajectory` (beware: the aggregate CSV "Avg" column is judge-mean and diverges when a component is missing — always read per-scenario fields). **RQ1 reports its judge signals side by side, with no composite as headline** (`RQ1_SIGNALS` in `07_pool_ladder_runs.py`): `addie_median` is the LEAD because ADDIE measures instructional-design content quality — the construct the research question is about — while `trajectory_score` measures process conformance, a different construct, and `total_score`'s 0.7/0.3 weights come from the benchmark rather than from this study. All three get identical statistics (3 failure policies, Holm per signal×policy) under `comparisons.by_signal[<signal>]`; `total_score` is kept in full for comparability with ISD-Agent-Bench's own reporting. No signal is an endpoint — all three appear side by side in the abstract and main tables; do NOT phrase the ADDIE narrative lead as a "chosen endpoint" or "post-hoc decision" (user 2026-08-04); the construct-match rationale carries it. Multi-judge by default (`--single-judge` to disable). Context-aware weighting in `metrics/context_weights.py`. `metrics/alignment.py` holds the **RQ2 constructive-alignment evaluation protocol**: deterministic, no LLM in measurement, **NO similarity threshold anywhere**, and reported as a **flat panel with NO primary endpoint**, whose members and size are defined once in `PANEL_SIGNALS` (6 signals as of 2026-08-30 — never restate the count in prose, it goes stale) — calling one signal "primary" is an implicit composite. Two mechanically independent instrument families, each with its own sensitivity axis: **A, textual correspondence** — exactly the three edges of the Biggs triad: `objective_assessment_similarity` (C2), `objective_activity_similarity` (C3), `activity_assessment_similarity` (C4), all continuous mean-max **rectified** cosine, `max(0, cos)` on [0,1] — a scale choice, not a matching cutoff, never describe it as raw cosine. **B, cognitive demand** (`objective_cognitive_congruence`, `porter_mean`, `webb_bloom_consistency` — no similarity involved). **Both families measure the SAME three edges**: `PORTER_PAIRS` is `objective_assessment` / `objective_activity` / `activity_assessment`, so the families differ by instrument and by nothing else. **Removed outright 2026-08-30** (not kept as diagnostics — dead code around a measurement crawls back into tables): `objective_evaluation_similarity`, `assessment_objective_similarity`, the `objectives↔evaluation` Porter pair, `extract_evaluation_texts`, `counts["evaluation"]`, `NON_PANEL_DIAGNOSTICS`, `NON_DIRECTIONAL_SIGNALS`. Evaluation-phase text mirrors no core graph relation, so no signal reads it; note `porter_mean` therefore CHANGED DEFINITION and old `porter_*` numbers are not comparable. **Naming rule**: a signal is named after the operation it computes, because names get read on figure axes and slides where a name that asserts more than the operation does the work only the validity evidence earns — so "alignment" names the protocol and the `aligned(o)` legs but never a metric, and nothing is called "precision" (that implies a retrieval frame needing a threshold this protocol lacks). Collective terms (2026-08-29): benchmark judge values = "LLM judge score(s)", panel values = "alignment score(s)" — per-metric names unchanged. Multiplicity is reported twice per size: `p_holm` within one signal (6 comparisons) and `p_holm_panel` over the whole panel×baseline family. **Degenerate input splits two ways (2026-08-30)**: a set the agent never produced (no objectives / items / activities) is an AGENT failure and scores **0.0 + note** on every signal that references it — including the Bloom-derived ones — while a set that exists but carries no Bloom-classifiable text is an INSTRUMENT limit and stays `None`. Collapsing the two let the worst outputs leave the pooled denominator instead of scoring against the agent, and parse-failure rates rise as the model shrinks, so the missingness tracked RQ1's independent variable. `activity_assessment_similarity` (C4) never depends on objectives and is always computed. RQ2 pooling mirrors RQ1's failure policies: the complete-case layer is over *available* outputs, never call it unconditional; `06` always records a `missing_outputs` roster and `07` always reads it to add a failure=0 pass — run over a results dir via `scripts/alignmentgraph-isd-bench/06_score_alignment.py`. Instruments are **preset-only**: encoders from `ENCODER_PRESETS` (`--encoder-preset(s)`/`--all-encoders`), Bloom classifiers from `BLOOM_PRESETS` (`--bloom-preset(s)`, `--bloom-checkpoint`); `--all-arms` runs the whole sweep. With no flag it runs the primary configuration `nemotron` + `bertbloom`. The sweep is a **star, not a grid** — each arm deviates from the primary on exactly one axis (5 arms, not 8). The primary Bloom arm `bertbloom` is a single 6-way softmax `bert-base-uncased` head fine-tuned on the EDM2022CLO corpus of Li et al. 2022 — their corpus, not their classifier design: their notebooks yield either six independent binary heads or one multi-label sigmoid head, both of which need an extra decision layer to produce the single level per text the panel requires. Measured on a held-out split it reaches kappa 0.926 vs the lexicon's 0.650, which is why it is primary; the cost, which must be declared, is that its per-case level assignment is no longer traceable to Anderson & Krathwohl and family B is no longer bit-wise deterministic (a discrete argmax, so fp noise can flip a label rather than nudge a number). **It needs a checkpoint on disk** (`evaluator/scripts/train_bloom_6way_classifier.py`, ~15 min locally), so alignment scoring is no longer zero-setup; a missing checkpoint SKIPS the arm rather than falling back to the lexicon. The `lexicon` arm is the sensitivity axis for family B (3 of the 6 panel signals are Bloom-derived, so without it that family is checked by no axis) and costs no GPU (`--bloom-presets lexicon --embed-cache-only`); the two arms agree at only kappa 0.665, so neither mirrors the other. Each encoder preset also pins its **backend**: only the 8B primary `nemotron` is served (`api`, endpoints from per-slot `<SLOT>_EMBED_BASE_URLS` written by `05_sync_embed_pod_env.py`, or `--embed-base-urls-for SLOT=...` — deliberately no shared endpoint/model/revision variable); `bgem3`/`granite` run `local` in-process via sentence-transformers (measured on an M4 Pro: ~44 and ~25 min for the ladder's 335k unique texts), `tfidf` is pure Python. So the pod is needed only while the primary arm is scored. Never embed one model on two backends: the cache key is `sha1(model[@revision]+text)` and does not record the backend, so mixing sources is silent. Full metric definitions: `docs/benchmark_guides.md` Appendix A.

## Common commands

All commands run from inside `isd-agent-benchmark/`. The `scripts/` number prefixes follow pipeline order; shared scripts sit in `scripts/`, the ladder pipeline in `scripts/alignmentgraph-isd-bench/`, the ablation pipeline in `scripts/alignmentgraph-isd-bench/ablation/`. The full workflow (incl. audits and paper-table generation) is in `docs/benchmark_guides.md`.

```bash
# One-time setup: creates venv, installs base deps + every agent + evaluator (editable)
```

## Conventions

- Much of the benchmark code, docstrings, and CLI help is in **Korean** (the domain is Korean instructional-systems design). Match the surrounding language when editing a file. `docs/` (guide, summary) is Vietnamese/English.
- "Scenario" (benchmark) and "design brief" (`alignmentgraph_isd`) refer to the same input; the only translation point is `_scenario_to_design_brief` in the benchmark's `agents/alignmentgraph-isd` adapter. Prefer the "design brief" vocabulary inside the package.
- Numbers reported in the paper must come from the generated artifacts (`09_gen_paper_tables.py` output), never typed by hand.
- **Generated artifacts are English with a decimal point.** Every caption, column header, table footnote, `\newcommand` comment and `stats_*.md` heading in `results/generated/` is English (in-figure text always was); numbers render `87.77`, not `87,77`. `fmt_num()`/`size_display()` in `09_gen_paper_tables.py` (and 11's own copies) enforce the decimal mark — do not reintroduce a `.replace(".", "{,}")`. `99_audit_artifacts.py` check I fails RED on Vietnamese letters or a `{,}` decimal in any artifact.
- **Captions state what the table shows and what a cell is** — roughly 100–250 chars. Methodological justification ("why this metric", "how the arms were run") belongs in the methods section, not in a caption.
- **A mean and its ±SD must come from the same signal.** The pooled per-agent dict carries `run_to_run_sd_{addie,traj,total}`; `RQ1_SD_FIELD` in `09_gen_paper_tables.py` maps each mean to its own SD. The bare `run_to_run_sd` is Total, kept only because `ablation/08_pool_ablation_runs.py` checks A0 drift on `total_score` — never pair it with an ADDIE or Trajectory mean.
- **Any table cell averaged over a partial scenario set must disclose it.** RQ1 tables print `n` per cell with a starred footnote; the RQ2 tables and panel do the same (RQ2's `n` counts scenarios with *at least one* scored run — a weaker condition than RQ1's all-3-runs complete case, so the two are labelled distinctly).

## The `alignmentgraph-isd` package (thesis core)

Located in `alignmentgraph-isd/src/alignmentgraph_isd/`. **The full pipeline is the default and only preset** (the former `HARNESS_ABLATION` preset system was removed in the 2026-07 RQ pivot; do not reintroduce it). **There is ONE executor (2026-08-31 pivot, `control_mode` removed 2026-09-03)**: every ADDIE stage is a NATIVE tool-calling act→observe loop (`core/agentic/`), and `core/runner.py::MetaAgent` dispatches there. The pre-pivot LangGraph StateGraph pipeline, its `core/workflow.py`, its `core/agents/` specialists and the `alignmentgraph-isd-scripted*` benchmark ids were all removed 2026-09-01; nothing selects an executor, so do not reintroduce a `control_mode` field. The ADDIE stage ORDER is instructed identically in both decomposition arms (`loop._WORKFLOW_OVERVIEW`) — the agents are autonomous in HOW a stage runs, never in what order the stages run. For the ablation study, `HarnessRunConfig` carries two axes, defaults = the full pipeline: `agent_mode` (`"multi"` | `"single"` — decomposition, and **deliberately a BUNDLE, disclosed exactly as `context_mode` is** (2026-09-01, when the single arm became a ReAct loop): it varies the context boundary, who walks the stages, how many personas, and whether work is delegated. That is what "multi-agent vs single-agent" means to a reader, and pretending it is one variable would be the overclaim. `multi` starts each stage in a fresh context under that stage's specialist identity; `single` carries ONE context across all six under `SingleDesignerAgent`. **Equal model effort is NOT the parity requirement** — an agent that plans its own order and writes its own item batches cannot spend the same number of calls as a harness walking a fixed plan with Developers, so a call-count difference is the treatment, not a confound. What IS checkable, and what the claim rests on, is that neither arm was CUT by its turn budget (`test_the_agentic_arms_are_two_shapes_not_two_settings`); while that holds, an outcome difference cannot be blamed on the ceiling. The registered directional prediction: quality degrades with STAGE POSITION in `single` and not in `multi`, widening as the model shrinks; read it off `metadata.autonomy`) and `context_mode` (`"graph"` | `"prose"` — the alignment machinery **as a bundle**: `"prose"` runs a graph-free `ProseStore` blackboard (`core/prose_store.py`) where each step deposits its whole parsed JSON under one document key and later steps read documents back verbatim by a static read-list; safeguards reduce to the 6 within-artifact checks + shared self-repair/regen (and note two of the six families — activity, content — carry ONLY cross-artifact checks, so in prose they get no self-validation and no repair at all); no docket, no audit, and NO `graph`/`graph_dot` result keys — instead `result["prose"]` carries the raw blackboard dump, saved as `<agent_id>_prose.json` (inspection artifact, not an audit). Never implement prose as a renderer/adapter over the graph — that was the retired 2026-08 design and it made the axis measure surface form only). Axes are set solely via the benchmark's per-arm agent registrations (`alignmentgraph-isd-single-prose`, `-single-graph`, `-multi-prose` in `run_benchmark.py`), and the resolved axes are recorded in `metadata.run_config`.

Public API (see the package README for details):

```python
from alignmentgraph_isd import DesignBrief, HarnessRunConfig, MetaAgent
result = MetaAgent(config).run(brief)   # config.llm_factory is REQUIRED — hard error, never silent empty output
# result keys: addie_output, trajectory, metadata, graph, graph_dot
```

Layout:

- **`config.py`** — `HarnessRunConfig`: `llm_factory` (any LangChain chat-model factory, required), `use_rag` + `retrieval_subagents` (RAG gate, both required to open it), `regen_budget`/`regen_backoff_seconds` (re-run a specialist whose section came back with empty required fields; the benchmark adapter sources these from `BENCHMARK_DELAY` / `HARNESS_REGEN_*` env), `llm_max_concurrency`/`llm_min_interval_seconds` (the outbound-call gate, `core/ratelimit.py`), `llm_context_window`/`llm_completion_reserve` (the transcript budget, derived from the SERVING window rather than fixed: `prompt_token_budget()` = `window - reserve` is the invariant and is identical for both arms, and `history_budget()` converts it to the characters `trim_history` counts through `TokenRatio` — chars-per-token MEASURED on this run's own traffic from the `prompt_tokens` every response reports, not a constant and not a tokenizer library (`tiktoken` is OpenAI's vocabulary while the ladder serves Qwen, so it would be a different estimate rather than a correct one, and the real tokenizer means pulling `transformers` into a package the benchmark installs plain). Cached per run like `ratelimit.gate_for`, so both arms calibrate off the same traffic; a measurement never raises the estimate above the pessimistic `COLD_CHARS_PER_TOKEN = 3.0`, because the budget is a safety limit and a prompt that does not fit fails outright while an under-estimate only costs retained history. Unset window keeps the historical `HISTORY_CHAR_BUDGET = 24000`; on the ladder's 16384/8192 it starts at 24576 and sharpens. The adapter sources both from `AGENT_MODEL_CONTEXT_WINDOW` / `AGENT_MODEL_MAX_TOKENS_CAP`). **The harness itself is now fully SEQUENTIAL** — nothing in `core/` runs LLM calls concurrently (the only `ThreadPoolExecutor`s left are RAG's parallel retrieval plans and the server's run executor), so this gate does not currently bind. It is kept because it answers a MEASURED failure of the LangGraph pipeline, where the multi arm's Content and Rubric Designers shared a superstep and each fanned out one Developer call per work set: one agent peaked at ~12 concurrent requests while the benchmark's `-r` posture counted it as ONE unit, and a shared endpoint answered the overflow with HTTP 429 on the two multi arms (9–25 per run over three runs) against 0–2 on the sequential single arms — a throttling handicap sitting on the `agent_mode` axis itself. Re-introducing any concurrent fan-out brings that back. The gate is per-run, never process-wide (a shared one would make one arm queue behind another and inflate its `execution_time_seconds`). Default 0 = unbounded standalone; `run_benchmark.py` stays free of any agent's internal knobs — it publishes only its own posture (`BENCHMARK_RATE_LIMIT` + `BENCHMARK_DELAY`), and the adapter owns the mapping (`LLM_CONCURRENCY_BY_RATE_LIMIT`: conservative 2 / moderate 3 / aggressive 4 / turbo 6, else 4), overridable with `HARNESS_LLM_MAX_CONCURRENCY` (0 opts out). `llm_min_interval_seconds` is off by default and deliberately NOT wired to `BENCHMARK_DELAY` — that is a between-agents delay, not a per-call one.

Two passthroughs between a caller and the executor were removed 2026-09-05: `run_workflow` here, and the `run_design_brief` wrapper in the package root — each took the same arguments, returned the same dict and chose nothing. The `llm_factory` guard moved onto `MetaAgent.run` with the second one, which is where it should always have been: the benchmark adapter calls `MetaAgent` directly and so was the one caller running unattended without the check.

A LEAF on purpose — these sat in `runner.py` until 2026-09-05, which made `runner ↔ agentic` a cycle held open by a deferred import; nothing here imports `core/agentic/` or `core/runner.py`.
- **`core/alignment_graph/`** — the AlignmentGraph subsystem as a package (since 2026-08-26; exactly the bundle the `context_mode` axis ablates — a prose run USES nothing from it; `NodeType` is imported module-level as an artifact-family key, but every real graph call is gated on `context_mode` and a prose run holds `graph = None`): `graph.py` holds `AlignmentGraph`/`NodeType`, `alignment.py` the relation registry + establishers, `audit.py` the `GraphAuditor` residual audit, `viz.py` the node-link/DOT dumps; `AlignmentGraph`/`NodeType` are re-exported at the package root. `AlignmentGraph` is the alignment-dependency graph of ISD artifacts. Edge type = human-readable relation key in `"<id>-<verb>"` form (e.g. `"C2-assessed_by"`, `"P10-delivers"`); **16 relations total: 5 core (`C1`–`C5`) + 11 secondary (`P1`–`P11`)**, defined once in `core/alignment_graph/alignment.py::REGISTRY`. Core relations are the construct-validity backbone and each carries a `theory` citation (Constructive Alignment / Backward Design); secondary relations are provenance and traceability only, and are never claimed as construct-validity evidence. **C6/C7 and `NodeType.RUBRIC` were retired 2026-09-02**: a rubric criterion is not an independent artifact but a FIELD of the assessment item it marks (`fanout._attach_to_parent` files it there at commit time, on either substrate — the join `aggregate._shape_rubrics` does by id, never needing the graph). As nodes they produced two core relations that could not fail — C6 was recorded from the very commit that created both ends, and C7 was C6 composed with C2 because `RULES_RUBRICS` requires the criterion to name its item's own objective — and both read coverage 1.0 in all 28 recorded runs. A relation that cannot fail is not construct-validity evidence, so the backbone is five that genuinely break rather than seven of which two are guaranteed. Gone with them: `orphan_rubric` (a criterion cannot be orphaned when it lives inside its item), `alignment.match_id` (C7 was its only caller), the audit's `unevaluated_objectives`, and the rubric leg of `viz.objective_alignment` — which never narrowed `aligned` because it was true for every objective that had an item at all. `rubric_consistency` and `evidence_alignment` STAY, reading the criteria off the items in one implementation shared by both substrates. Every ELEMENT node must be reachable by some relation — SECTION nodes are singleton documents or narrative residues ONLY (2026-08-27: the legacy full-list sections objective_0/activity_0 were retired and assessment_0 removed outright; element nodes are the single source of truth for every item list, and repairs read/write elements directly). Narrative sections (gap_0/topic_0/constraint_0/improvement_0) connect to their elements via structural `narrates` edges (non-registry, the `precedes` class: dump/DOT/webapp navigation for the human auditor; never read by docket, checks or coverage). `development.expert_review` is ALWAYS synthesized by the aggregator from the verification that actually ran (self-validation rounds + repairs + relation coverage; prose arm: rounds/repairs only) — the model-authored review was removed from every generation schema 2026-08-27 (a same-model same-call review of artifacts that don't exist yet is fiction, and collided with the separate REAL expert-validation package). `to_full_dict()` / `to_dot()` produce the per-run graph dump (saved as `<agent_id>_graph.json` / `.dot` in benchmark results) — this is the auditability contribution. Prose-arm runs build no graph and ship no dump — that absence is the reported auditability contrast.
- **`core/agentic/`** — the executor: `loop.py` (`AgenticLLM` with a `bind_tools` path + `ToolLoop`, the act→observe loop; `STAGE_MAX_TURNS=12` (= `ToolLoop.MAX_TURNS`; `fanout.DEVELOPER_MAX_TURNS=6`, `REPAIR_TURNS=3`), `SUBMIT_BUDGET=3`, `HISTORY_CHAR_BUDGET=24000` and `trim_history`, which drops the OLDEST tool observations first and keeps the system turn and the live stage), `tools.py` (real OpenAI-shape tool schemas per stage per context mode; `submit`'s parameter schema is the artifact's TOP-LEVEL keys from `AgenticStep.submit_fields`, a strictly weaker front line than `validate`, never a second source of truth; `coerce_args` parses string-encoded structured arguments at the transport boundary, choosing the parser by the DECLARED shape (`llm_io.parse_json_array` for an array, `parse_json_response` for an object) — the latter returns a dict from every path including one that decodes the first complete object and stops, so on a malformed array it hands back element one; measured, an array of three assessment items closing `..."]}` instead of `..."}]` came back as a single dict and only the caller's type check kept one item from being committed as the whole set. `parse_json_array` scans top-level `{...}` blocks by brace balance and parses each independently, so one malformed element costs that element, and returns how many it dropped rather than swallowing it — the qwen3_coder parser reconstructs the CALL, not the value types the schema declares, and without this every stage of every arm fell to the fallback). **ONE SUBMIT TOOL PER ARTIFACT** (`tools.submit_specs`, 2026-09-03): a stage binds `submit_assessment_plan` and `submit_assessment_dev_plan`, and `implementation` binds six. This is the `analysis` piecemeal declaration generalized — the reason is the 8192 completion cap, and a rejected artifact now costs that artifact rather than the whole stage. Three things had to move with it or the split loses work: every `commit_*` MERGES into its section (`_merge_section`/`_merge_document`; `add_node` replaces, so `submit_dev_plan` after `submit_assessment_plan` would leave only the dev plan), every validator judges ONLY what arrived but still rejects an EMPTY submit (`_nothing_arrived` — without it `validate({})` is clean and `unwrap_section`, which treats "the validator accepted it" as "already unwrapped", commits the `{"artifact": …}` wrapper it exists to undo), and completion is `parts_of(step)` asked of the STATE (otherwise `outcomes` returns after `submit_course_goal` and never gets its objectives). An OPTIONAL artifact gets exactly ONE nudge per stage — `media_selections` (P8 and its rubric item), `non_instructional_strategies` and `dev_plan` used to travel in the same payload and would otherwise never be sent — bounded at one because a model with nothing more answers a repeated ask with a repeated nothing. The commit label names the artifact (`design_implementation_instructor_guide`) or six identical entries read to the judge as redundancy, and a submit that re-sends what is already committed logs `duplicate_submit` rather than a second design step. `_wrap_bare_artifact` accepts the artifact without its envelope when the tool has exactly one field (measured on the replan loop). **The `dev_plan` the model submits used to be THROWN AWAY**: `commit_assessment` stripped it, `commit_activities` ignored it, and `_dispatch_payload` reads the fan-out's input back out of the graph — so assessment and activities reported `source=fallback` on every run and the agent's own grouping, its `instrument_hint`/`block_theme` and the `expected_activities` field added for it reached nothing. It is kept on the plan section (the graph dump shows an auditor how the family was divided) and stripped at aggregation (`aggregate._HARNESS_ONLY_SECTION_KEYS`). **There is no separate generation step: the artifact IS the `submit` tool call's arguments.** That is why `check_artifact` was removed 2026-08-31 — it ran the same validator a rejected `submit` runs and returned the same errors, but cost a full re-emission of the artifact each call (measured: 17-18 calls per single-arm run); the retry allowance lives in `SUBMIT_BUDGET` (3) instead, where it is explicit and equal across arms. `specialists.py` (the stage table, graph AND prose commits, `SINGLE_PERSONA`/`SINGLE_IDENTITY`; **one role per stage since 2026-09-01** — `analysis` runs under `NeedsAnalystAgent`/`needs_analyst`, not as the Outcome Designer's second job, because front-end analysis and outcome design are different ADDIE phases and a role that spans two is the seam a reviewer pushes on. `needs_analyst` owns NO checks and is therefore absent from `repairs.OWNED_BY_FAMILY` entirely — read that table with `.get`. **`AgenticStep.submit_parts` declares an artifact that may be submitted PIECEMEAL** — only `analysis` (its five top-level objects were one call, the largest artifact in the system, and a 2B model hit the 8192-token cap mid-arguments): the validator judges only the parts that arrived, `specialists.missing_parts(step, state)` asks the STATE what is still missing (never a loop counter — regen resets one and the arms would disagree), `step_done` is all-parts-present, `ToolLoop` keeps the turn after an accepted partial submit and names what is left (cap = one turn per part + `PART_SUBMIT_SLACK`), and `AgenticStep.parts_block()` composes the instruction FROM the declaration so both arms get identical wording. Splitting the artifact not the STAGE keeps `stage_order` at six and forces no extra call. `commit_analysis_prose` had to become a top-level MERGE: `ProseStore.put` overwrites, so a second instalment dropped the first — graph mode never had the bug, so leaving it would have put a data loss on the `context_mode` axis itself), `run.py` (`run_agentic_brief`: both axes, the reconciliation pass, `metadata.autonomy`). Guards that must never be dropped — each answers a MEASURED failure on a 2B model: the anti-loop repeat guard, submit rejection returning the exact deterministic errors, truncation salvage (the 8192 completion cap), and `step_done`. **There is no scripted fallback** (removed 2026-09-01): it composed up to 76% of the prose arm's committed artifacts, existed on `ToolLoop` but never on `ReactLoop` — so it caught one side of the decomposition axis and dropped the other — and calling an arm agentic while a single-shot wrote most of its output is a construct claim the trace does not support. A step that produces nothing sets `gave_up`, commits the best the MODEL managed (`_give_up`'s `last_resort`, never harness-written text) and lets the deterministic repair net mend it; the count is itself a finding rather than something hidden inside a fallback rate. Commits deep-copy the submitted section: node data would otherwise ALIAS the tool-call arguments that stay in the transcript, so a later repair would silently rewrite what the agent is shown to have said.
- **`core/rag/`** — external-corpus retrieval (`agent.py`, `planner.py`, `sandbox.py`).
- **`core/memory.py`** — what a run REMEMBERS, in one object: `transcripts` (every context published, per agent — the `agent_mode` axis read rather than asserted), the live substrate (`graph` XOR `store`, asserted in the constructor because holding both would let a prose run read the graph), and `plans` (each Designer's division of its family into work sets, ROUND BY ROUND), and `findings` — every DISTINCT violation of the run with what became of it (2026-09-04). A finding's identity is `checks.Violation.key`, built from the SUBJECT (type + node + the metadata that says which one it is) and never from the EVIDENCE: `bloom_mismatch_assessment.metadata["item_ids"]` grows as Developers commit while the problem stands, so a key including it would report the old finding closed and a new one opened. Content-addressed rather than minted like `new_agent_run_id`, because a violation is re-derived from state by a pure function every round and has no continuous object to carry an id. `Finding.outcome` is `open`/`repaired_by_harness`/`repaired_by_agent` with `report_only` ORTHOGONAL to it (`REPORT_ONLY` constrains the harness, not the agent, so "report-only and repaired by the agent" is reachable and is the evidence the agent tier does what the net cannot), and `open_reason` (`converged`/`budget`/`unowned`/`unseen`) is **the line between a result about the MODEL and a parameter we chose** — reporting them merged would be a wrong claim. Precedence `unowned > budget > converged` so a reconciliation that trivially converges on a type it may not touch cannot relabel "we cut it short" as "the model could not do it". Repair credit is a before/after key DIFF, never a match on repair events: `repairs._log_repair` is called with a CLASS id in most routines, so joining on node_id would credit nobody. Served as `result["violations"]`, `violations.json` and `GET /runs/{id}/violations`. Two of the three barely existed before: a transcript was published only to the optional `on_event` consumer, so the CLI and the benchmark ran whole ladders whose contexts existed nowhere afterwards; a plan lived for one call of `_run_fanout` and was dropped, so nothing could answer "which Developer was asked for what". `Memory.of(state)` wraps a bare substrate for a caller that only has one. `state` stays bound to the SUBSTRATE everywhere in `run.py` — half that module asks `hasattr(state, "element_nodes")` to tell the arms apart, and a wrapper that does not answer it puts every graph run down the prose branch. Returned as `result["contexts"]` / `result["plans"]` and NEVER merged into `trajectory`: the judge reads that and transcripts alone would multiply its size by the number of turns.

The stage roles survive as identities in `core/agentic/specialists.py` (`NeedsAnalystAgent`, `OutcomeDesignerAgent`, `AssessmentDesignerAgent`, `ActivityDesignerAgent`, `ContentDesignerAgent`, `ImplementationPlannerAgent`, and `SingleDesignerAgent` for the single arm); the fan-out lives in `core/agentic/fanout.py` + `core/dev_plans.py`. **Shared substrate rule (2026-08-26)**: `rulebook.py` (per-family generation SCHEMA/RULES) and `repairs.py` (repair toolbox + `OWNED_BY_FAMILY`) are the single sources both decomposition arms compose from — the multi arm's stage steps build persona+schema+rules prompts from the rulebook, and `SingleDesignerAgent` composes the same `RULES_*` blocks (via `rules_for(state)` for the `outcomes` state, by direct concatenation elsewhere) rather than reusing any stage's own prompt assembly. **RULES parity is test-enforced; SCHEMA parity is NOT** — the single arm's per-state JSON exemplars are hand-written and are weaker than `rulebook.SCHEMA_*` in places (e.g. `_TASK_ASSESSMENT_ITEMS` shows one `performance_task` exemplar against `SCHEMA_ASSESSMENT_ITEMS`' three, omitting `multiple_choice` with `options`/`correct_answer`), which plausibly biases the `item_completeness` check against that arm. Closing this needs a SCHEMA-parity assertion alongside the existing RULES one in `tests/test_ablation_flags.py`. Repairs run via `repairs.repair(family, violations, ctx)` under the calling agent's own identity. **Work sets keep the objective grouping and are then subdivided WITHIN it by PLANNED QUANTITY × estimated element size** (`dev_plans.UNIT_CHARS` × `SET_OUTPUT_BUDGET` → `max_units(family)`). The planned quantity comes from the rule already in force per family, not from a guess: assessment = pairs in the set (`RULES_ASSESSMENT_ITEMS_SET`: one item per pair), content = the module's media selections (`RULES_MATERIALS_UNIT`: a material realizes one of them), activity = `expected_activities`, which the planner is asked for (added to `SCHEMA/RULES_ACTIVITY_DEV_PLAN` 2026-09-01) because no rule fixes how many activities an objective needs — and is clamped by `_expected()` to [1, `MAX_EXPECTED_PER_SET`] with the measured yield as fallback, never trusted. Splitting the FLAT obligation list would cut across objectives (the tail of ILO-01 with the head of ILO-02), discarding the grouping the plan chose, so a set breaks up by objective first and only an objective that is still too large is batched within itself — **Scoping a set is the PLANNER's job, not the backstop's**: `RULES_ACTIVITY_DEV_PLAN` states the per-block budget (interpolated from `max_units("activity")` itself, never hand-written — a planner held to a different number than the split uses gets its grouping taken apart behind it) and requires several distinctly-themed blocks for an objective needing more than one call, since each block is written by a developer that cannot see the others. The deterministic split remains a last resort: it carries a divided quota (plan 10 at limit 8 is 2x5, never 2x8) and names the theme it is carving up, and `stats["oversized_splits"]` on the `dev_plan` event counts how often it fired — the only number separating a plan doing its job from one the backstop is carrying. The activity count cap is relative to PLANNED ACTIVITIES, not objectives: based on objectives it allowed one block per objective and merged two correctly scoped blocks back into one, discarding the themes that kept them apart. Both halves of the estimate are measured (element sizes and yield-per-obligation) and are estimates from one scenario — revisit against ladder data. The size bound is applied AFTER the count cap and WINS over it: `_cap_and_number` merged overflow into one tail set, so the cap on the number of calls made the calls unanswerable (33 objectives × 3 categories = 12 sets with a tail carrying 88 obligations in ONE call; now 22 sets of at most 6). Set count may therefore exceed `MAX_SETS_HARD_CAP` — an oversized set loses everything it was going to produce, an extra call costs one call. `repairs.OWNER_BY_VIOLATION` is the reverse index of `OWNED_BY_FAMILY` (asserted non-overlapping at import) and is what routing addresses violations by. **A repair never writes instructional content of its own (2026-09-01), and since 2026-09-03 it never calls the model at all.** Every routine in `repairs.py` is *structural*: it rearranges what the design already holds (C4/P5, the evidence rule, the Bloom verb from the taxonomy, a dangling C2/P3 item re-pointed, a keyless choice item reformatted as `short_answer`). A violation that needs WRITING goes back to its owning agent as a repair turn inside that agent's own tool loop (`ToolLoop._own_violations` → `_repair_request`, bounded by `REPAIR_TURNS`), so the request, the model's answer and the artifact are three consecutive turns of ONE transcript. The generative repairs that used to live here (`_llm_repair_items`, `_llm_item_options`, `_llm_formative_methods`, `_llm_pilot_data_plan`, and `repair_plan_coverage`/`repair_assessment_items`/`repair_formative_methods`/`repair_pilot_data_plan` with them) composed a **second conversation under a second system prompt with no tools bound, published in the owning agent's name** — visible in the webapp's Context tab as a extra block for that agent. That is not a display artefact: the context boundary IS the `agent_mode` axis, so a repair path opening its own boundary sat inside the treatment, and it did so only for the families that had generative repairs, in proportion to how badly a run had gone. Gone with them: `RepairContext.call_llm`, `run.py::_ObservedLLM`, `run.py::_CarriedContextLLM`, and `repair_unfilled` (which can no longer fire; the enum stays so old trajectories still read). Guarded by `tests/test_one_agent_one_system_prompt.py` — one system prompt per agent across every published context, and no published context without bound tools — plus the `RepairContext`-field/`call_llm`-source assertion in `tests/test_no_invented_content.py`. `REPORT_ONLY` is now a statement about the HARNESS only: those types are shown to their owning agent like any other violation (the agent can write what is missing) and are simply never touched by the deterministic net. There is no other kind of repair: the templated stand-ins that used to close a gap (`OBSERVABLE_RUBRIC`, `OBSERVABLE_DESCRIPTION`, `FALLBACK_METHODS`, `_fallback_item_text`, `_fallback_pilot_data_plan`, the "Guided practice for ILO-01" activity, the "Support module for TLA-01" module) were each satisfying their own check by existing — the objection that had always kept P6 audit-only, applied consistently. The consequence is deliberate and is `repairs.REPORT_ONLY` (`C3 C5 P4 P6 activity_engagement bloom_mismatch_activity rubric_consistency feasibility actionability`): those types stay in `OWNED_BY_FAMILY` so reconciliation names an owner, are filtered out in `repair()` **before** dispatch (three family dispatchers each silently dropped them once their template went), and are counted as residual. Residual counts and `ready_to_aggregate: false` therefore rise — that is the number becoming honest, not a regression. A repair that changed nothing also logs nothing: a `repair` event reporting no change is what made `repair_success_rate` unreadable. Guarded by `tests/test_no_invented_content.py` (AST guard on module-level prose constants + behavioural round-trip per report-only type). The precedent: synthesising a missing assessment item deterministically copied the objective's own `statement` into the item's `question`, which the RQ2 `objective_assessment_similarity` signal read as near-perfect correspondence — and since these are cross-artifact repairs that only the graph arm runs, the artefact sat on the `context_mode` axis itself (fixed 2026-08-30). **The objective's Bloom level field is `level`, not `cognitive_process`** (renamed 2026-08-30): the evaluator's `extract_objectives` reads `level`, so under the old name `bloom_vs_declared_agreement` was `null` on every alignmentgraph arm and family B's sanity check never ran. Assessment items keep `required_cognitive_process` and activities `learner_cognitive_process`. The `bloom` check now also validates `level` against Bloom's six — an out-of-taxonomy value short-circuited the verb comparison and passed silently. **A gap its Developers leave goes back to the DESIGNER, which answers with a PLAN** (`core/agentic/replan.py`, 2026-09-03). Work sets now commit ONE AT A TIME as each Developer finishes, so the family's output is visible to the checks while the Designer's own loop is still there to be continued. The orchestrator then checks the family, and every gap a new work set could close (`C2 P3 plan_coverage` for assessment, `C3 C4` for activities; `content` is absent because its checks are structural or report-only) is put to the Designer as a repair turn ON ITS OWN MESSAGE LIST — the answer is a `dev_plan`, never artifacts, because a Designer plans and a Developer writes. The round's ground truth is the GAPS (`replan.gap_targets` builds coverage targets from the violation metadata; normalizing against the family would re-derive every set it already has) and its set ids carry a round suffix (`AS-01R1`; without it `committed_set_ids` sees the round-0 id and skips every new set, so the round runs and produces nothing). `REPLAN_ROUNDS = 1`: a gap that survives a re-plan plus a fresh Developer call is one the model cannot close, and asking again is how a stage becomes a hang. Measured on the test fixture: +6 calls on the multi arm, 4 new work sets, `plan_coverage` residual 0. **Because a Developer self-commits, its artifacts' IDS are reserved rather than negotiated**: **the model does not write one at all** — the id field is gone from `SCHEMA_ASSESSMENT_ITEMS`/`SCHEMA_ACTIVITIES`/`SCHEMA_MATERIALS`, and every id COMPOSES the set's ordinal with the artifact's own — `AT-0203` is the third artifact of the second work set (`WorkSet.ordinal`, `dev_plans._composite_id`). The set's half is fixed by `_cap_and_number` when the plan is numbered, before any Developer runs; each set counts its own artifacts from 1, so the numbering is DENSE (a single reserved range per set leaves gaps — set 1 stopping at `AT-10` and set 2 starting at `AT-21` — and that gap is a block boundary showing through into the deliverable). Asking the model for an id was pure cost: it was overwritten every time, so it bought nothing, while every malformed one (`AT-{`, a duplicate, one copied out of the schema example) was a real failure — and the field's absence shortens the artifact it has to fit under the completion cap. **Same-family references are therefore POSITIONAL**: an activity's `prerequisite_activities` names activities in the block the model is submitting by 1-based position (`[1]` = the first it wrote), resolved to the assigned ids by `dev_plans._resolve_positions`, which DROPS anything that does not resolve (a dangling id in the graph is invisible; a dropped reference shows in the coverage numbers). That field was already broken for the same underlying reason — it was never declared a reference field, so every one of them reached the graph naming a renumbered-away id: **measured 0 of 3 resolving** on the test fixture, while `fanout._establish` reads exactly it to build the `precedes` edges. `SetOutput.ref_fields` is replaced by `self_ref_fields` (the old entries were all CROSS-family — objective, assessment and module ids — which need no remapping and never got any). A replan round strides the ordinal (`ROUND_ORDINAL_STRIDE = 50`, so round 1 writes `AT-5101`), and a scan past `taken` is the backstop for a Developer that used one id twice inside its own set. The old rule was "keep the model's id, rename it only if someone already took it", which was fine while the family landed in one batch (the winner was plan order, deterministic) and became "whoever committed first" under per-set commits — the same thing today, since the fan-out is sequential, and a different thing the moment anything runs sets concurrently or retries one. `commit_sets` also runs inside one `AlignmentGraph.transaction()` (re-entrant RLock): reading the ids in play and then writing nodes chosen from what was read is only correct if nothing lands in between. **Ids stay SHORT (`AT-0203`, never `AT-01-AS-02`)**: every cross-artifact edge here is a model-written id reference (an item names its objective, an activity the item it prepares for, the implementation plan the activities it schedules), so a long or unguessable id raises the failure rate of every one of them on exactly the small models the study is about — a namespacing scheme was tried and broke P10/P11 outright. What makes renumbering safe is that **every family that references another READS it first** (the activity Developer's `developer_reads` include ASSESSMENT; the ImplementationPlanner reads ACTIVITY/MATERIAL and its docket lists the P10/P11 gaps by id), so a reference is written against committed ids rather than against the schema example. Same-set references follow the renumbering through `SetOutput.self_ref_fields`; a canned cross-reference does NOT, which is why the test fixture resolves ids from state (`conftest._named_from_prompt`). Guarded by `tests/test_id_safety.py`. Related: `step_done` now honours `AgenticStep.done`, because a work set's family pool fills up as its SIBLINGS commit and the default guard called set 2 finished before its Developer had spoken. **Cross-family violations are reconciled ONCE after the last stage** (`core/agentic/run.py::_reconcile`, bounded by `SELF_VALIDATION_BUDGET` rounds, immediately before `GraphAuditor`): each residual violation is stamped with its owner from `repairs.OWNER_BY_VIOLATION` onto `Violation.target_designer` and handed to that family. The pass is deterministic and model-free — it takes no LLM and cannot open a context of its own; routing names the owner so the trace records who a residual violation belongs to, and the structural fixes it dispatches are identical on either side of both axes. Routing exists only in graph mode: prose runs the 6 within-artifact checks, all owned by the family that just ran, so it has nothing cross-family to route — that asymmetry is a PREDICTED interaction (decomposition should pay off more under `graph`) and must be pre-specified, not discovered. Never re-enter mid-pipeline: route→repair→recheck is no longer bounded by the stage order, and unbounded on an SLM it is a hang. `tests/fixtures/golden_prompts.json` pins every composed prompt AND every bound tool schema byte-for-byte (under native tool calling the schemas are half of what the model sees, so both are comparability surface) — a deliberate wording change means regenerating the fixture, never letting prompts drift. The single source of truth for the ADDIE output contract is `validation.py` (`_ADDIE_PHASE_FIELDS`/`_SECTION_FIELDS`); the former `schema/addie_output.json` + warning-only jsonschema pass duplicated a strictly weaker subset of it and was removed 2026-08-25.
- **`server/` + `webapp/`** — the **demo web app** (FastAPI + React/Vite/Cytoscape), added 2026-08-06. See `server/README.md`. It is **strictly optional and must stay that way**: its dependencies live in the `[server]` extra, `alignmentgraph_isd/__init__.py` never imports `.server`, and `cli.py` imports it lazily inside the `serve` subcommand. The benchmark installs this package plain, so FastAPI/uvicorn/SQLModel must never become hard dependencies — `tests/test_import_isolation.py` is the guard, and `99_audit_artifacts.py`-style discipline applies: if that test fails, the experiment environment is about to get polluted. Run it with `./run-app.sh` (or `alignmentgraph-isd serve`) — single process only, since live runs are in-process state, so there is deliberately no `--workers` flag. Configured by `AGISD_SERVER_*`. The model lives in the app's own Model settings dialog as a **list of connections** with exactly one active (`server/llm_settings.py`, `LLMConnection`): each carries a base URL, key, and the model picked on it, because a model id belongs to the endpoint that serves it. That model is chosen from a dropdown read off the endpoint's own `/v1/models` (`GET /api/connections/{id}/models`) — addressed by connection id so the key is looked up server-side and never travels with the request. The app is **OpenAI-compatible only** and passes `api_spec` explicitly, so `AGENT_MODEL_API_SPEC` cannot reach in and change the client under a connection configured here; `core/llm.py` keeps its Anthropic branch for the CLI and benchmark. `AGENT_MODEL_*` **seeds the first connection** on an empty database (`seed_from_environment`, called from the lifespan) rather than acting as a live fallback — once a row exists the database is the whole story, so a connection deleted in the dialog does not return on restart. The API key is stored in clear text in the local SQLite file and never returned to the browser (only `has_api_key`). There are no migrations (`init_db` is `create_all`), so the retired single-row `LLMSetting` table just sits dead in an old `demo.db`. A model *name* alone yields a usable factory but not a usable model, so the app constructs the client up front in `/api/health` and before starting a run — without that a run starts, every specialist fails, and it "completes" in milliseconds with an empty graph under a `succeeded` label.

**The artifact contract is FETCHED, not pushed (2026-09-03).** A stage turn now carries the task and a pointer; the exact schema and rules are behind a `stage_brief` tool bound by `tool_specs` and answered by `ToolLoop._execute`. Two things follow. The turn no longer grows with the schema, so it can be compacted like anything else — which is what lets `trim_history` protect only the system turn. And **both arms fetch the same way**: `multi` used to be handed its schema free while `single` spent a call on `stage_brief`, a harness-imposed asymmetry sitting on the decomposition axis, which is the one kind of cost difference that IS a confound. It costs `multi` what `single` always paid (measured on the test fixture: 31 → 45 calls). A fan-out WORK SET is the exception (`AgenticStep.contract_inline`): its loop is at most `DEVELOPER_MAX_TURNS` on one assignment and never reaches the window, so fetching would buy it nothing and cost a call per set — plus nine identical `tool_stage_brief` entries under one Developer identity, which the trajectory judge scores as redundancy. The stage loop's `stage_brief` takes no argument (it is already in its stage) and is LABELLED with the stage name for the same redundancy reason; the single arm's takes one, which is also how the test fixture tells the arms apart.

**Compaction (2026-09-03).** `trim_history` protects the system turn and the compaction note, and nothing else — the stage turn is droppable on purpose, since protecting it would pin a block at the front of the very window it has to make room in. What makes that safe is the rest of the design: the task survives as content in the summary, the schema was never in the turn (`stage_brief`), and the tool menu is redundant with the binding, which goes out with every request. Compaction leaves a NOTE (`compaction_note`, protected from the next trim and rewritten rather than doubled) saying how many turns went, that their findings are re-readable from the design state, and — via `core/agentic/compaction.py` — a ROLLING model-written summary of them, each fold taking the previous summary plus what just went so the note stays one fixed-size block and each call's input stays bounded. The call is the ORCHESTRATOR's (the agent did not choose to compact and is never shown it, so it is not published as one of that agent's contexts, though `AgenticLLM` still counts its tokens), and failure is always safe: an unusable answer keeps the previous summary and the count note stands. **The arms pay for this very differently, and that is the point** — `single` carries one conversation all run and reaches compaction far sooner than `multi` — so the trigger, prompt, budget and fallback are ONE implementation both call identically, and `autonomy.compactions`/`compaction_summaries` report the price per stage. A cost that differs because of the mechanism is the effect being measured; only one the harness imposed would be a confound. `tools.tool_menu` is now RENDERED FROM `tool_specs` so the two cannot disagree: written by hand it still announced one `submit` after the per-artifact split, so every stage of every arm named a tool that was not bound and `_submit_alias` was silently rescuing it. And a loop's published `_specs` are ACCUMULATED across the conversation (`_merge_specs`), because a binding shrinks — the replan round binds only `submit_dev_plan`, and `react_specs` drops a stage's submit once it is complete — so publishing the live binding alone made a context claim the agent never had the tool it had just used.

**Contexts stream LIVE (2026-09-03).** Each loop republishes its context after every turn (`ToolLoop._publish(live=True)` / `ReactLoop`), so the app's Context tab fills in and its meters move while the agents are still working instead of a row appearing only once its agent has finished. Three things keep it affordable: the per-turn publish is skipped entirely when nobody is watching (`TrajectoryLogger.is_observed` — the emit is a no-op without a consumer but SERIALIZING the transcript to build one is not, and a benchmark run must not pay it); `RunState.add_context` and `Memory.remember_context` UPSERT by the context's `id`, or `result["contexts"]` would be a pile of prefixes of itself — that id is an AGENT RUN id (`core.memory.new_agent_run_id`), minted where the CONVERSATION begins and carried on the loop, so it travels in every snapshot and neither the server nor the browser has to know what a context's identity is made of. **Not derived from what the context is about**: the first version hashed `(agent, phase, label, attempt)`, and the replan round — which continues the Designer's own message list under a new step name — hashed to a different id, so the tab showed that conversation as TWO rows with the second containing the first. Same system prompt in both, so `test_one_agent_one_system_prompt` passed it; the split had simply moved from the prompt to the label, and `test_one_conversation_is_one_context` is the guard for that half. A loop that CONTINUES another's messages inherits everything that describes the CONVERSATION rather than the task — `agent_run_id`, `label`, `compacted`, and `attempt` (the only such caller is `run._replan_rounds`). `attempt` counts REGENS; numbered from the replan round instead, a perfectly healthy Designer counted as twice-run. It is data, not a label — the tab surfaced it as a "retry #N" badge and that was worse than nothing, since every reader who saw it had to work out whether something had gone wrong, while the rows are already in publication order so one stage's attempts read top to bottom unaided; a regen, a fan-out work set and each arm's design loop all start a fresh message list and so get their own. The transcript export addresses a context by that id (`?context=`) rather than by position, which is only stable once the run is over; **auto-compaction is SHOWN, not counted**: `trim_history` returns the messages it dropped (not a count), the loop accumulates them in `compacted`, and `compacted_transcript` republishes the whole conversation in order with those turns flagged `compacted: true` — dimmed and badged in the tab, and deliberately NOT in the token figures, which measure what is being sent. The dropped run is contiguous and starts right after the system message, which is what lets the order be rebuilt as `[system] + everything dropped so far + what is left` with no positional bookkeeping. Before this, a trimmed transcript answered "what was this agent shown" for the LAST call only and everything earlier was gone but for `history_dropped`, a number saying how much was lost and nothing about what. A loop that continues another's messages inherits its `compacted` too. The SSE frame carries `contexts_light()` — the rows WITHOUT their transcripts, which is the whole of the list view — with the transcripts and the TOOL SCHEMAS fetched per row from `/contexts?context=<id>` when a reader opens one, and re-fetched as that row grows — so a listed row costs almost nothing and the one being looked at is live. (The schemas are half of what the model sees and are excluded from the frame for the same size reason as the transcript; when live rows first landed, the Tool schemas section rendered empty because it was reading a row that by design has none.) `add_context` deliberately does NOT `_notify()`: waking the stream once per turn drained it far ahead of the events.jsonl flusher and turned a rare disk-replay race into a reliable one; the frame rides the next event's wakeup, and `llm_started`/`llm_finished` bracket every model call. That race is also fixed at its root — `_flush_state` now runs BEFORE `state.finish()`, which is what closes the live stream, so nothing is left unflushed when a reader returns.

**Live progress (`on_event`).** `MetaAgent.run` takes an optional keyword-only `on_event(kind, payload)` consumer, wired through `TrajectoryLogger`. It is purely additive — with no consumer every emit is a no-op and the recorded trajectory is byte-for-byte what it was — and exists because the harness is synchronous and one run takes 4–7 minutes, so a UI has nothing to show otherwise. Beyond mirroring the recorded streams it emits `phase_started`/`phase_finished` (from `core/agentic/run.py`) and `llm_started`/`llm_finished` (from `core/agentic/loop.py::AgenticLLM`), which record nothing but are the only signal during the ~50 s a single model call takes, plus `graph_snapshot`. A consumer that raises is swallowed; `HarnessCancelled` (a `BaseException`) is the deliberate exception and is how the app stops a run. **A `graph_snapshot` payload must be consumed synchronously** — it aliases the live graph, which later phases keep mutating.

**RAG = external-corpus retrieval only, and it is on-demand.** `use_rag` is off by default and off on the benchmark. When enabled, retrieval is NOT performed upfront: retrieval is a TOOL (`retrieve`) the agent chooses to call and writes the query for, so the pre-agentic separate decision call is subsumed by that choice (`loop.ToolLoop._retrieve` → `core/rag/planner.py::RetrievalPlanner` over `core/rag/agent.py` retrieval agents; `core/rag/sandbox.py` still executes multi-agent plans). The tool is gated exactly like the old path — on the benchmark it is not even offered. Graph-context retrieval (the AlignmentGraph subgraph) is core, always on, and is **not** called RAG.

## The benchmark (`isd-agent-benchmark/`)

`run_benchmark.py` is the orchestrator. Key facts that aren't obvious from the README:

- **Agents run in-process, not as subprocesses.** `_get_agent_runner(agent_id, llm_config)` imports each agent's Python class directly and returns a `run(scenario) -> dict` closure. The CLI interfaces documented in `shared/interfaces/agent_interface.md` exist but the benchmark does not use them. Agent `src/` paths are added to `sys.path` at the top of `run_benchmark.py`.
- **The evaluator IS run as a subprocess** (`isd-evaluator`), with stdout streamed to parse `__EVAL_PROGRESS__` markers.
- Each agent must return `{"addie_output": ..., "trajectory": ..., "metadata": ...}`. Output schemas live in `shared/schemas/*.json`. The metadata saved in `*_trajectory.json` carries uniform `token_usage` + `execution_time_seconds` for every agent. **Token accounting follows the `LLMConfig` object lineage**: `_get_agent_runner` opens one scope per run with `LLMConfig.new_token_scope()`, `copy_with()` re-shares the counter (as it does the credential/endpoint round-robin), and `run_benchmark` reads `resolved_llm_config._token_counter` after the runner returns. `copy_with()` used to hand out a FRESH counter and the runner leaned on that side effect, which silently required agents never to copy the config they were handed — all six baselines copy it in `__init__` to pin model/temperature, so every one of them reported `token_usage` 0 from 2026-08-29 until this was fixed 2026-08-31, while `alignmentgraph-isd` kept real numbers because its own copy sits behind an `if max_tokens is None` guard the uniform max_tokens never trips. `shared/tests/test_token_accounting_reaches_agents.py` constructs all seven agents and asserts each ends up on the run's counter; only `09/11_gen_*_tables.py` never read tokens, so no paper number was affected — `15_gen_facts_sheet.py` was.
- **`shared/llm`** is the single source of LLM configuration. Agents must NOT read provider env vars or instantiate `ChatOpenAI`/`ChatAnthropic` directly — call `create_chat_model(llm_config)` / `llm_config_from_env()`. `LLMConfig.api_spec` is the API *contract* (`openai_compatible`/`anthropic`), distinct from `provider` (a backend preset label). Add providers via config, not agent code.
- `shared/llm/factory.py` also implements the three serving-protection env flags used for the self-hosted ladder (uniform across all agents — fairness): `AGENT_MODEL_MAX_TOKENS_CAP` (ladder value **8192**), `AGENT_MODEL_STREAMING=1`, `AGENT_MODEL_DISABLE_THINKING=1`.
- Agent vs. judge models are configured **separately** (`AGENT_MODEL_*` vs `JUDGE_MODEL_*`) to avoid self-preference bias. Judge config supports comma-separated lists aligned across names/providers/URLs, with `|` grouping multiple credentials per judge.
- Agent env-quads for the self-hosted Qwen pods (`QWEN{08B,2B,4B,9B}_AGENT_MODEL_*`) live in a **marker-managed block at the end of `.env`**, written by `scripts/3_sync_runpod_pods_env.py` (read-only against the RunPod API). Never hand-edit that block.
- Results land in `results/<dataset>_benchmark_<model>_<run_tag>_<ts>/` (e.g. `test_90_benchmark_Qwen3.5-2B_r1_...`) or `results/single_<ts>/` for single scenarios. Both launchers take `RUN_TAGS` (comma/space-separated, run sequentially per slot).

### Evaluator (`evaluator/`)

`isd_evaluator` package. ADDIE rubric scoring: 33 Context-Matrix sub-steps → 13 consolidated items → 5 ADDIE phases (100 pts), plus BFCL-based trajectory scoring; per-scenario `total_score = 0.7·ADDIE + 0.3·Trajectory` (beware: the aggregate CSV "Avg" column is judge-mean and diverges when a component is missing — always read per-scenario fields). **RQ1 reports its judge signals side by side, with no composite as headline** (`RQ1_SIGNALS` in `07_pool_ladder_runs.py`): `addie_median` is the LEAD because ADDIE measures instructional-design content quality — the construct the research question is about — while `trajectory_score` measures process conformance, a different construct, and `total_score`'s 0.7/0.3 weights come from the benchmark rather than from this study. All three get identical statistics (3 failure policies, Holm per signal×policy) under `comparisons.by_signal[<signal>]`; `total_score` is kept in full for comparability with ISD-Agent-Bench's own reporting. No signal is an endpoint — all three appear side by side in the abstract and main tables; do NOT phrase the ADDIE narrative lead as a "chosen endpoint" or "post-hoc decision" (user 2026-08-04); the construct-match rationale carries it. Multi-judge by default (`--single-judge` to disable). Context-aware weighting in `metrics/context_weights.py`. `metrics/alignment.py` holds the **RQ2 constructive-alignment evaluation protocol**: deterministic, no LLM in measurement, **NO similarity threshold anywhere**, and reported as a **flat panel with NO primary endpoint**, whose members and size are defined once in `PANEL_SIGNALS` (6 signals as of 2026-08-30 — never restate the count in prose, it goes stale) — calling one signal "primary" is an implicit composite. Two mechanically independent instrument families, each with its own sensitivity axis: **A, textual correspondence** — exactly the three edges of the Biggs triad: `objective_assessment_similarity` (C2), `objective_activity_similarity` (C3), `activity_assessment_similarity` (C4), all continuous mean-max **rectified** cosine, `max(0, cos)` on [0,1] — a scale choice, not a matching cutoff, never describe it as raw cosine. **B, cognitive demand** (`objective_cognitive_congruence`, `porter_mean`, `webb_bloom_consistency` — no similarity involved). **Both families measure the SAME three edges**: `PORTER_PAIRS` is `objective_assessment` / `objective_activity` / `activity_assessment`, so the families differ by instrument and by nothing else. **Removed outright 2026-08-30** (not kept as diagnostics — dead code around a measurement crawls back into tables): `objective_evaluation_similarity`, `assessment_objective_similarity`, the `objectives↔evaluation` Porter pair, `extract_evaluation_texts`, `counts["evaluation"]`, `NON_PANEL_DIAGNOSTICS`, `NON_DIRECTIONAL_SIGNALS`. Evaluation-phase text mirrors no core graph relation, so no signal reads it; note `porter_mean` therefore CHANGED DEFINITION and old `porter_*` numbers are not comparable. **Naming rule**: a signal is named after the operation it computes, because names get read on figure axes and slides where a name that asserts more than the operation does the work only the validity evidence earns — so "alignment" names the protocol and the `aligned(o)` legs but never a metric, and nothing is called "precision" (that implies a retrieval frame needing a threshold this protocol lacks). Collective terms (2026-08-29): benchmark judge values = "LLM judge score(s)", panel values = "alignment score(s)" — per-metric names unchanged. Multiplicity is reported twice per size: `p_holm` within one signal (6 comparisons) and `p_holm_panel` over the whole panel×baseline family. **Degenerate input splits two ways (2026-08-30)**: a set the agent never produced (no objectives / items / activities) is an AGENT failure and scores **0.0 + note** on every signal that references it — including the Bloom-derived ones — while a set that exists but carries no Bloom-classifiable text is an INSTRUMENT limit and stays `None`. Collapsing the two let the worst outputs leave the pooled denominator instead of scoring against the agent, and parse-failure rates rise as the model shrinks, so the missingness tracked RQ1's independent variable. `activity_assessment_similarity` (C4) never depends on objectives and is always computed. RQ2 pooling mirrors RQ1's failure policies: the complete-case layer is over *available* outputs, never call it unconditional; `06` always records a `missing_outputs` roster and `07` always reads it to add a failure=0 pass — run over a results dir via `scripts/alignmentgraph-isd-bench/06_score_alignment.py`. Instruments are **preset-only**: encoders from `ENCODER_PRESETS` (`--encoder-preset(s)`/`--all-encoders`), Bloom classifiers from `BLOOM_PRESETS` (`--bloom-preset(s)`, `--bloom-checkpoint`); `--all-arms` runs the whole sweep. With no flag it runs the primary configuration `nemotron` + `bertbloom`. The sweep is a **star, not a grid** — each arm deviates from the primary on exactly one axis (5 arms, not 8). The primary Bloom arm `bertbloom` is a single 6-way softmax `bert-base-uncased` head fine-tuned on the EDM2022CLO corpus of Li et al. 2022 — their corpus, not their classifier design: their notebooks yield either six independent binary heads or one multi-label sigmoid head, both of which need an extra decision layer to produce the single level per text the panel requires. Measured on a held-out split it reaches kappa 0.926 vs the lexicon's 0.650, which is why it is primary; the cost, which must be declared, is that its per-case level assignment is no longer traceable to Anderson & Krathwohl and family B is no longer bit-wise deterministic (a discrete argmax, so fp noise can flip a label rather than nudge a number). **It needs a checkpoint on disk** (`evaluator/scripts/train_bloom_6way_classifier.py`, ~15 min locally), so alignment scoring is no longer zero-setup; a missing checkpoint SKIPS the arm rather than falling back to the lexicon. The `lexicon` arm is the sensitivity axis for family B (3 of the 6 panel signals are Bloom-derived, so without it that family is checked by no axis) and costs no GPU (`--bloom-presets lexicon --embed-cache-only`); the two arms agree at only kappa 0.665, so neither mirrors the other. Each encoder preset also pins its **backend**: only the 8B primary `nemotron` is served (`api`, endpoints from per-slot `<SLOT>_EMBED_BASE_URLS` written by `05_sync_embed_pod_env.py`, or `--embed-base-urls-for SLOT=...` — deliberately no shared endpoint/model/revision variable); `bgem3`/`granite` run `local` in-process via sentence-transformers (measured on an M4 Pro: ~44 and ~25 min for the ladder's 335k unique texts), `tfidf` is pure Python. So the pod is needed only while the primary arm is scored. Never embed one model on two backends: the cache key is `sha1(model[@revision]+text)` and does not record the backend, so mixing sources is silent. Full metric definitions: `docs/benchmark_guides.md` Appendix A.

## Conventions

- Much of the benchmark code, docstrings, and CLI help is in **Korean** (the domain is Korean instructional-systems design). Match the surrounding language when editing a file. `docs/` (guide, summary) is Vietnamese/English.
- "Scenario" (benchmark) and "design brief" (`alignmentgraph_isd`) refer to the same input; the only translation point is `_scenario_to_design_brief` in the benchmark's `agents/alignmentgraph-isd` adapter. Prefer the "design brief" vocabulary inside the package.
- Numbers reported in the paper must come from the generated artifacts (`09_gen_paper_tables.py` output), never typed by hand.
- **Generated artifacts are English with a decimal point.** Every caption, column header, table footnote, `\newcommand` comment and `stats_*.md` heading in `results/generated/` is English (in-figure text always was); numbers render `87.77`, not `87,77`. `fmt_num()`/`size_display()` in `09_gen_paper_tables.py` (and 11's own copies) enforce the decimal mark — do not reintroduce a `.replace(".", "{,}")`. `99_audit_artifacts.py` check I fails RED on Vietnamese letters or a `{,}` decimal in any artifact.
- **Captions state what the table shows and what a cell is** — roughly 100–250 chars. Methodological justification ("why this metric", "how the arms were run") belongs in the methods section, not in a caption.
- **A mean and its ±SD must come from the same signal.** The pooled per-agent dict carries `run_to_run_sd_{addie,traj,total}`; `RQ1_SD_FIELD` in `09_gen_paper_tables.py` maps each mean to its own SD. The bare `run_to_run_sd` is Total, kept only because `ablation/08_pool_ablation_runs.py` checks A0 drift on `total_score` — never pair it with an ADDIE or Trajectory mean.
- **Any table cell averaged over a partial scenario set must disclose it.** RQ1 tables print `n` per cell with a starred footnote; the RQ2 tables and panel do the same (RQ2's `n` counts scenarios with *at least one* scored run — a weaker condition than RQ1's all-3-runs complete case, so the two are labelled distinctly).

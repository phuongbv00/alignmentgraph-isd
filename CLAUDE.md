## The `alignmentgraph-isd` package (thesis core)

Located in `alignmentgraph-isd/src/alignmentgraph_isd/`. **The full pipeline is the default and only preset** (the former `HARNESS_ABLATION` preset system was removed in the 2026-07 RQ pivot; do not reintroduce it). **There is ONE executor (2026-08-31 pivot, `control_mode` removed 2026-09-03)**: every ADDIE stage is a NATIVE tool-calling act→observe loop (`core/agentic/`), and `core/runner.py::MetaAgent` dispatches there. The pre-pivot LangGraph StateGraph pipeline, its `core/workflow.py`, its `core/agents/` specialists and the `alignmentgraph-isd-scripted*` benchmark ids were all removed 2026-09-01; nothing selects an executor, so do not reintroduce a `control_mode` field. The ADDIE stage ORDER is instructed identically in both decomposition arms (`protocol.WORKFLOW_OVERVIEW`) — the agents are autonomous in HOW a stage runs, never in what order the stages run. For the ablation study, `HarnessRunConfig` carries two axes, defaults = the full pipeline: `agent_mode` (`"multi"` | `"single"` — decomposition, and **deliberately a BUNDLE, disclosed exactly as `context_mode` is** (2026-09-01, when the single arm became a ReAct loop): it varies the context boundary, who walks the stages, how many personas, and whether work is delegated. That is what "multi-agent vs single-agent" means to a reader, and pretending it is one variable would be the overclaim. `multi` starts each stage in a fresh context under that stage's specialist identity; `single` carries ONE context across all six under `SingleDesignerAgent`. **Equal model effort is NOT the parity requirement** — an agent that plans its own order and writes its own item batches cannot spend the same number of calls as a harness walking a fixed plan with Developers, so a call-count difference is the treatment, not a confound. What IS checkable, and what the claim rests on, is that neither arm was CUT by its turn budget (`test_the_agentic_arms_are_two_shapes_not_two_settings`); while that holds, an outcome difference cannot be blamed on the ceiling. The registered directional prediction: quality degrades with STAGE POSITION in `single` and not in `multi`, widening as the model shrinks; read it off `metadata.autonomy`) and `context_mode` (`"graph"` | `"prose"` — the alignment machinery **as a bundle**: `"prose"` runs a graph-free `ProseStore` blackboard (`core/prose_store.py`) where each step deposits its whole parsed JSON under one document key and later steps read documents back verbatim by a static read-list; safeguards reduce to the 6 within-artifact checks + shared self-repair/regen (and note two of the six families — activity, content — carry ONLY cross-artifact checks, so in prose they get no self-validation and no repair at all); no `read_alignment_state` tool (the graph arm PULLS one role-scoped state read — rows with ids, the gaps its output must close, its own open issues — and is pointed at it when issues remain; the prose arm reads whole documents and is PUSHED its within-artifact violations as a `repair_request`), no audit, and NO `graph` result key — instead `result["prose"]` carries the raw blackboard dump, saved as `<agent_id>_prose.json` (inspection artifact, not an audit). Never implement prose as a renderer/adapter over the graph — that was the retired 2026-08 design and it made the axis measure surface form only). Axes are set solely via the benchmark's per-arm agent registrations (`alignmentgraph-isd-single-prose`, `-single-graph`, `-multi-prose` in `run_benchmark.py`), and the resolved axes are recorded in `metadata.run_config`.

Public API (see the package README for details):

```python
from alignmentgraph_isd import DesignBrief, HarnessRunConfig, MetaAgent
result = MetaAgent(config).run(brief)   # config.llm_factory is REQUIRED — hard error, never silent empty output
# result keys: addie_output, trajectory, metadata, graph
```

Layout:

- **`config.py`** — `HarnessRunConfig`: `llm_factory` (any LangChain chat-model factory, required), `use_rag` + `retrieval_subagents` (RAG gate, both required to open it), `regen_budget`/`regen_backoff_seconds` (re-run a specialist whose section came back with empty required fields; the benchmark adapter sources these from `BENCHMARK_DELAY` / `HARNESS_REGEN_*` env), `llm_max_concurrency`/`llm_min_interval_seconds` (the outbound-call gate, `core/ratelimit.py`), `llm_context_window`/`llm_completion_reserve` (the transcript budget, derived from the SERVING window rather than fixed: `prompt_token_budget()` = `window - reserve` is the invariant and is identical for both arms, and `history_budget()` converts it to the characters `trim_history` counts through `TokenRatio` — chars-per-token MEASURED on this run's own traffic from the `prompt_tokens` every response reports, not a constant and not a tokenizer library (`tiktoken` is OpenAI's vocabulary while the ladder serves Qwen, so it would be a different estimate rather than a correct one, and the real tokenizer means pulling `transformers` into a package the benchmark installs plain). Cached per run like `ratelimit.gate_for`, so both arms calibrate off the same traffic; a measurement never raises the estimate above the pessimistic `COLD_CHARS_PER_TOKEN = 3.0`, because the budget is a safety limit and a prompt that does not fit fails outright while an under-estimate only costs retained history. Unset window keeps the historical `HISTORY_CHAR_BUDGET = 24000`; on the ladder's 16384/8192 it starts at 24576 and sharpens. The adapter sources both from `AGENT_MODEL_CONTEXT_WINDOW` / `AGENT_MODEL_MAX_OUTPUT_TOKENS`). **The harness is SEQUENTIAL BY DEFAULT** — `fanout_workers = 1` — and the gate then has nothing to bind. `HarnessRunConfig.fanout_workers > 1` (adapter env `HARNESS_FANOUT_WORKERS`, unset on the ladder) is the one opt-in concurrency: `core/runner.py::_run_fanout` runs one family's Developers on a `ThreadPoolExecutor` capped by `llm_max_concurrency`, and still COMMITS every set in plan order on the driver's thread, so the graph's insertion order — and every listing and aggregate list read off it — is identical whatever the worker count (`tests/test_fanout.py::test_parallel_workers_produce_the_same_graph_as_sequential`). Wall time only: calls, tokens and artifacts do not change, and `metadata.run_config.fanout_workers` says which a results dir ran. What made it safe: `TrajectoryLogger` gives every non-owner thread its own attribution scope seeded from the root (a worker inherits the phase, sets its own actor), one `_log_lock` guards every append and the numbering read off it, and `Memory` locks its mutators. The gate is kept because it answers a MEASURED failure of the LangGraph pipeline, where the multi arm's Content and Rubric Designers shared a superstep and each fanned out one Developer call per work set: one agent peaked at ~12 concurrent requests while the benchmark's `-r` posture counted it as ONE unit, and a shared endpoint answered the overflow with HTTP 429 on the two multi arms (9–25 per run over three runs) against 0–2 on the sequential single arms — a throttling handicap sitting on the `agent_mode` axis itself. An UNBOUNDED concurrent fan-out brings that back, which is why `fanout_workers` is capped by this gate. The gate is per-run, never process-wide (a shared one would make one arm queue behind another and inflate its `execution_time_seconds`). Default 0 = unbounded standalone; `run_benchmark.py` stays free of any agent's internal knobs — it publishes only its own posture (`BENCHMARK_RATE_LIMIT` + `BENCHMARK_DELAY`), and the adapter owns the mapping (`LLM_CONCURRENCY_BY_RATE_LIMIT`: conservative 2 / moderate 3 / aggressive 4 / turbo 6, else 4), overridable with `HARNESS_LLM_MAX_CONCURRENCY` (0 opts out). `llm_min_interval_seconds` is off by default and deliberately NOT wired to `BENCHMARK_DELAY` — that is a between-agents delay, not a per-call one.
- **`cli.py`** — `alignmentgraph-isd run` on a JSON file already in `DesignBrief` shape; builds a model from `--model-*` flags or `AGENT_MODEL_*` env vars.
- **`core/runner.py`** — `MetaAgent`, the ONLY entry point, AND the run itself (`MetaAgent.run` IS the run, over a dozen private module-level helpers, all merged in from `core/agentic/run.py` 2026-09-16 — the orchestrator and the helpers it orchestrates were in two modules, which would have made every helper public API for one caller had they stayed split; `core/agentic/` is now the executor's PARTS and this is the whole, and `core/agentic/__init__.py` deliberately exports nothing). Per node `label`/`kind`/`detail`/`level`/`repaired`; per edge `id`/`layer`/`tier`/`invalid`/`invalid_reason`; per objective an ordered `legs` list (`alignment.ALIGNMENT_LEGS`, from which `aligned` is DERIVED rather than written out again). **A leg is named ONLY by its relation** — `ALIGNMENT_LEGS` is just the ordered ids `("C2", "C3", "C4")`, the verb is `REGISTRY[id].edge_type` and the wording `REGISTRY[id].label`, and the per-objective scalars are those verbs (`assessed_by`/`practiced_by`/`prepares_for`, renamed 2026-09-14 from `measured`/`supported`/`prepares`, which were a third set of names for C2/C3/C4 living inside the very table meant to prevent a second; `viz._LEGACY_LEG_FLAGS` reads the old ones off an archived dump and is the only place they survive); plus a `legend` and a `schema_version`. The set's half is fixed by `dev_plans.number_sets` when the plan is numbered, before any Developer runs; **numbering and NAMING were fused inside `_cap_and_number` until 2026-09-06, and the one family that could not take the naming silently got no ordinal** — `material_work_units` does its own module-aware cap and keeps module-derived set ids (`MU-MOD-03`, read by `plan_set`, `pending_set_ids` and the graph dump), so it never went through it, every material set kept the dataclass default of 1, ids came out `MAT-0101`…`MAT-0108` across six modules, and uniqueness rested entirely on the `taken` scan — the exact "whoever commits first" scheme `_composite_id`'s own docstring rules out. `number_sets(sets, prefix="")` assigns the ordinal alone; `WorkSet.as_dict`/`work_set_from_dict` carry it too, or a round trip through `result["plans"]` resets it.  each set counts its own artifacts from 1, so the numbering is DENSE (a single reserved range per set leaves gaps — set 1 stopping at `AT-10` and set 2 starting at `AT-21` — and that gap is a block boundary showing through into the deliverable). Asking the model for an id was pure cost: it was overwritten every time, so it bought nothing, while every malformed one (`AT-{`, a duplicate, one copied out of the schema example) was a real failure — and the field's absence shortens the artifact it has to fit under the completion cap. **Same-family references are therefore POSITIONAL**: an activity's `prerequisite_activities` names activities in the block the model is submitting by 1-based position (`[1]` = the first it wrote), resolved to the assigned ids by `dev_plans._resolve_positions`, which DROPS anything that does not resolve (a dangling id in the graph is invisible; a dropped reference shows in the coverage numbers). That field was already broken for the same underlying reason — it was never declared a reference field, so every one of them reached the graph naming a renumbered-away id: **measured 0 of 3 resolving** on the test fixture, while `fanout._establish` reads exactly it to build the `precedes` edges. `SetOutput.ref_fields` is replaced by `self_ref_fields` (the old entries were all CROSS-family — objective, assessment and module ids — which need no remapping and never got any). A replan round strides the ordinal (`ROUND_ORDINAL_STRIDE = 50`, so round 1 writes `AT-5101`), and a scan past `taken` is the backstop for a Developer that used one id twice inside its own set. The old rule was "keep the model's id, rename it only if someone already took it", which was fine while the family landed in one batch (the winner was plan order, deterministic) and became "whoever committed first" under per-set commits — the same thing when the fan-out is sequential, and a different thing the moment anything runs sets concurrently (`fanout_workers > 1` does) or retries one. `commit_sets` also runs inside one `AlignmentGraph.transaction()` (re-entrant RLock): reading the ids in play and then writing nodes chosen from what was read is only correct if nothing lands in between. **Ids stay SHORT (`AT-0203`, never `AT-01-AS-02`)**: every cross-artifact edge here is a model-written id reference (an item names its objective, an activity the item it prepares for, the implementation plan the activities it schedules), so a long or unguessable id raises the failure rate of every one of them on exactly the small models the study is about — a namespacing scheme was tried and broke P10/P11 outright. What makes renumbering safe is that **every family that references another READS it first** (the activity Developer's `developer_reads` include ASSESSMENT; the ImplementationPlanner's state read lists ACTIVITY/MATERIAL rows and the P10/P11 gaps by id), so a reference is written against committed ids rather than against the schema example. Same-set references follow the renumbering through `SetOutput.self_ref_fields`; a canned cross-reference does NOT, which is why the test fixture resolves ids from state (`conftest._named_from_prompt`). Guarded by `tests/test_id_safety.py`. Related: `step_done` now honours `AgenticStep.done`, because a work set's family pool fills up as its SIBLINGS commit and the default guard called set 2 finished before its Developer had spoken. **Cross-family violations are reconciled ONCE after the last stage** (`core/runner.py::_reconcile`, bounded by `SELF_VALIDATION_BUDGET` rounds, immediately before `GraphAuditor`): each residual violation is stamped with its owner from `repairs.OWNER_BY_VIOLATION` onto `Violation.target_designer` and handed to that family. The pass is deterministic and model-free — it takes no LLM and cannot open a context of its own; routing names the owner so the trace records who a residual violation belongs to, and the structural fixes it dispatches are identical on either side of both axes. Routing exists only in graph mode: prose runs the 6 within-artifact checks, all owned by the family that just ran, so it has nothing cross-family to route — that asymmetry is a PREDICTED interaction (decomposition should pay off more under `graph`) and must be pre-specified, not discovered. Never re-enter mid-pipeline: route→repair→recheck is no longer bounded by the stage order, and unbounded on an SLM it is a hang. `tests/fixtures/golden_prompts.json` pins every composed prompt AND every bound tool schema byte-for-byte (under native tool calling the schemas are half of what the model sees, so both are comparability surface) — a deliberate wording change means regenerating the fixture, never letting prompts drift. The single source of truth for the ADDIE output contract is `validation.py` (`_ADDIE_PHASE_FIELDS`/`_SECTION_FIELDS`, plus `_NESTED_FIELDS` for the six implementation artifacts' INNER keys, held one level down at submit, audit and aggregate alike — added 2026-09-05 after run e81b8108 committed an `instructor_guide` under invented keys that passed every gate and, having no `session_guides`, established no P10/P11 edge; `specialists.validate_implementation` was also a no-op then, its filter testing the node-type token instead of the artifact's. One path is exempt at SUBMIT and only there: `instructor_guide.session_guides`, which the stage no longer writes — the contract is unchanged for the audit and for `validate_addie`, which see the document the aggregator joins the guide nodes back into); the former `schema/addie_output.json` + warning-only jsonschema pass duplicated a strictly weaker subset of it and was removed 2026-08-25.
- **`server/` + `webapp/`** — the **demo web app** (FastAPI + React/Vite/Cytoscape), added 2026-08-06. See `server/README.md`. It is **strictly optional and must stay that way**: its dependencies live in the `[server]` extra, `alignmentgraph_isd/__init__.py` never imports `.server`, and `cli.py` imports it lazily inside the `serve` subcommand. The benchmark installs this package plain, so FastAPI/uvicorn/SQLModel must never become hard dependencies — `tests/test_import_isolation.py` is the guard, and `isd-exp audit artifacts`-style discipline applies: if that test fails, the experiment environment is about to get polluted. Run it with `./run-app.sh` (or `alignmentgraph-isd serve`) — single process only, since live runs are in-process state, so there is deliberately no `--workers` flag. Configured by `AGISD_SERVER_*`. The model lives in the app's own Model settings dialog as a **list of connections** with exactly one active (`server/llm_settings.py`, `LLMConnection`): each carries a base URL, key, and the model picked on it, because a model id belongs to the endpoint that serves it. That model is chosen from a dropdown read off the endpoint's own `/v1/models` (`GET /api/connections/{id}/models`) — addressed by connection id so the key is looked up server-side and never travels with the request. The app is **OpenAI-compatible only** and passes `api_spec` explicitly, so `AGENT_MODEL_API_SPEC` cannot reach in and change the client under a connection configured here; `core/llm.py` keeps its Anthropic branch for the CLI and benchmark. A connection also carries the SERVING WINDOW and the token cap (`context_window`, `max_tokens`), which `llm_settings.window_settings()` turns into `HarnessRunConfig.llm_context_window` / `llm_completion_reserve` — read alongside the factory in `start_run` and frozen for the run, and the reserve IS the cap the client sends rather than a second field that could disagree with it. **The app reads no `AGENT_MODEL_*` at all** (2026-09-05): not as a seed, not as a fallback, not to fill a blank — `build_factory` passes `read_env=False` (added to `core/llm.py` for exactly this) and resolves every default itself, because a value arriving from the shell appears neither in the dialog nor in the database, so what the UI shows and what a run uses could differ with nothing on screen to say so. A connection saved with no key fails here rather than borrowing `AGENT_MODEL_API_KEY` and working until it is started from a different shell. `AGISD_SERVER_*` is unaffected — those are server settings, not model configuration. On the wire every field is written including an explicit null (so an optional number can be unset); `api_key` alone is kept when omitted, since the browser is never given it to send back. The API key is stored in clear text in the local SQLite file and never returned to the browser (only `has_api_key`). There are no migrations (`init_db` is `create_all`), so the retired single-row `LLMSetting` table just sits dead in an old `demo.db`. A model *name* alone yields a usable factory but not a usable model, so the app constructs the client up front in `/api/health` and before starting a run — without that a run starts, every specialist fails, and it "completes" in milliseconds with an empty graph under a `succeeded` label.

**The artifact contract is PUSHED, in the stage's own turn (2026-09-06).** `stage_brief` was a bound tool from 2026-09-03 to 2026-09-06 and is gone from `tool_specs`, `react_specs` and both loops' dispatch. Fetching answered a real problem — the stage turn used to grow with the schema and sat at the front of the very window it had to make room in, and `multi` was handed its schema free while `single` spent a call on it, a harness-imposed asymmetry on the decomposition axis — but it bought that by making the contract LOSABLE with nothing to put it back, and run 2b9e911a is the bill: the brief went with the implementation stage's ninth turn, the model invented `instructor_guidance` and a dict `session_guides`, was rejected 8 times across 3 regens, `instructor_guide` never committed, and 14 P10/P11 gaps followed. What makes pushing safe now is `compact`'s `restore` plus `respec`: the turn is droppable like everything else and comes back when it goes. The merge also removed a real overlap — the pointer restated `step.intro`, which is the first thing `task_block` says — and costs neither arm a call (one per stage per arm saved). **`AgenticStep.contract_inline` is gone with it**: it existed to exempt a fan-out work set from fetching, and now every step's contract is in its turn. **ONE marker again** (`STAGE_BRIEF_HEADER` = `--- STAGE: <stage> ---`), because the turn IS the brief; `brief_stages`/`lost_briefs`/`respec`/`_restore_brief` read the stage name back out of it, which is what lets one implementation serve both arms. **The single arm has it INJECTED, one stage at a time** (`ReactLoop._offer_contract`), before the first model turn and again after each commit, with `_compact` releasing a finished stage's contract as its artifact lands — so exactly one is live at a time. All six at once is what `_system_prompt`'s docstring has always ruled out and it stays ruled out: measured, they are 27,193 characters, 95% of an 8,192-token prompt budget. The current stage is the first not-done in the INSTRUCTED ADDIE order, which both arms are given identically (`_WORKFLOW_OVERVIEW`), so this is the harness restating an order the agent already had. The cost is real and is the reason this was a deliberate call rather than an obvious cleanup: the single arm can no longer submit a stage out of turn with its schema in hand, though `react_specs` still offers every incomplete stage's submit. The test fixture told the arms apart by `stage_brief`'s signature and now tells them apart by whether a bound submit is named after a STAGE (no artifact shares a name with one) — without that, every single-arm test would have run down the stage-loop branch and still passed.

**The artifact's SHAPE moved into the tool call, out of the prompt (2026-09-08).** Until now the stage turn ALSO carried "must follow this EXACT schema:" plus a literal JSON-example block (`rulebook.SCHEMA_<FAMILY>`), duplicating what the bound `submit_*` tool's own `parameters` already declared — kept shallow on purpose (top-level key + generic type, `additionalProperties: True`) specifically so it would never fork from that text. The two cost double the tokens for the same information. `core/agentic/artifact_schemas.py` is now the SOLE declaration of an artifact's field-level shape (types, nesting, enums), and `tools._parameters_from` builds the tool `parameters` from it; `AgenticStep.task_block()` lost its schema paragraph and the 13 `SCHEMA_*` rulebook constants (plus the specialists.py string-splice `_SCHEMA_*_DISPATCH` that combined a plan schema with its dev-plan schema for display) went with them — `RULES_*` prose stays, since cross-field/referential/judgment-call constraints (an id that must exist in a sibling array, a dynamic item count, an ordinal comparison against a Bloom level) are not expressible as static JSON Schema. Two things keep this from forking into a second hand-maintained copy: for the six `implementation_plan` sub-artifacts, `artifact_schemas.py` DERIVES their `properties`/`required` from `validation._NESTED_FIELDS` rather than retyping them (`validation.py` stays the one upstream source; this is a read of it, never a restatement); and every enum value list is typed exactly once in `rulebook.py` (`BLOOM_LEVELS`, `BLOOM_VERBS`, `EVIDENCE_TYPES`, `PLAN_CATEGORIES`, alongside the pre-existing `MEDIA_TYPES`), read by both the JSON Schema's `enum` arrays and the `%`-interpolated `RULES_*` sentences that used to hand-type the same list. The one real naming wrinkle: `dev_plan` is the submit-field name reused across the assessment/activities/implementation stages for three DIFFERENT shapes, so `AgenticStep.schema_keys` (`{"dev_plan": "assessment_dev_plan"}` etc., set only on those three steps) resolves which `artifact_schemas.ARTIFACT_SCHEMAS` entry a field actually means — everywhere else the field name IS the lookup key. **The ADDIE shape is a FLOOR, not a mould (2026-09-18): an undeclared key is kept, and only a missing REQUIRED field is a fault.** `artifact_schemas._obj` no longer sets `additionalProperties: false`, the undeclared-key gate (`tools.undeclared_key_errors`, 2026-09-16) and its stripping are gone from both arms, and what a model writes beside the declared fields travels with the artifact into the design state and out through the aggregator into `addie_output.json`, unfiltered. The gate had been added after run 7ef3ed16 shipped one `anticipated_difficulties` entry's four fields at the top level of `assessment_plan`; both ways of enforcing it were then measured to cost the artifact's SUBSTANCE on a small model, which often writes real content under a name of its own — rejecting: `prototype_execution` refused three times over two invented keys and shipped invalid (runs 14a6b4c7, 9efc3cfa), one refusal of `learner_analysis` costing `analysis` a regen (run 4bb81369); dropping: `context_analysis` shipped `constraints: []` and `task_analysis` `topics: []` with 31 keys of analysis discarded beside them (run 1c0a4e81). A stray key reaching the LLM judge is the accepted cost. The fan-out Developer tier (`fanout.py`'s `assessment_tools`/`learning_activities`/`learner_materials`/`session_guides`) needed no separate change: `fanout.set_step()` builds an ordinary `AgenticStep` that runs through the same `task_block()`/`tools.submit_specs()`, so fixing the shared machinery fixed it too — `SetOutput.schema` (the JSON-example string field) is gone, `.rules` stays. `loop.py::ToolLoop._fill_single_key_object`'s "a bare string means this artifact's one field" heuristic, which used to `json.loads(step.schema)` to find single-property artifacts, now reads `tools.ARTIFACT_SCHEMAS[...]["properties"]` the same way.

**Compaction (2026-09-03, reworked 2026-09-05).** `trim_history` protects the system turn and the compaction note, and nothing else — the stage turn is droppable on purpose, since protecting it would pin a block at the front of the very window it has to make room in. What makes that safe is the rest of the design: what the task asked for is in the design state or named as still missing by the tool results, the schema IS in the turn again but comes back when a trim takes it (`restore` below, plus `respec` on a rejection), and the tool menu is redundant with the binding, which goes out with every request. **A trim drains to the LOW-WATER MARK** (`TRIM_LOW_WATER = 0.5` of the budget), not to just under it: measured on run e81b8108 the just-under policy refired on three consecutive turns of one stage, because every new observation put the history back over the line. Compaction leaves a NOTE (`compaction_note`, protected from the next trim and rewritten rather than doubled) saying how many turns went and that their findings are re-readable from the design state — and the repeat guard FORGETS every call whose result went with them (`forget_compacted_calls`), or the model is told to read again and refused for having already read. **A dropped stage BRIEF is put BACK (2026-09-06), not just announced.** The note's standing promise is true of a tool result and false of the contract, which is not in the design state at all: measured on run 2b9e911a, the brief went with the implementation stage's ninth turn, the model then invented `instructor_guidance` and a dict `session_guides`, was rejected 8 times across 3 regens, `instructor_guide` never committed, and every activity and material in the design was left unscheduled (14 P10/P11 gaps, all `converged` and all `shown_to_agent=0`). So `compact` takes a `restore` callback and re-appends the stage turn at the TAIL — newest, where the next trim (oldest first) will not take it — for any stage still being written (`ToolLoop`: its own; `ReactLoop`: only a stage with `missing_parts`, since a finished one's contract is deliberately released). Only if it FITS under the budget; otherwise the note names the stage and says the schema is gone, and it names ONLY what could not be put back. Re-attaching beats asking because it costs no turn and is certain to arrive, where an instruction costs a turn and depends on compliance — and that run is three regens of a model that did not comply. It is NOT protected in place: a `role: "tool"` message cannot be hoisted the way the note is (the assistant turn that made the call must precede it), the dropped run has to stay contiguous for `compacted_transcript` to rebuild order, and pinning it would fix a block at the front of the very window it has to make room in. **The dropped turns are folded into a model-written ROLLING SUMMARY, and compaction is a HOOK OF THE HARNESS (2026-09-08, `core/agentic/compaction.py`).** On by default, no flag, no preset. Each compaction folds the previous summary and the newly dropped turns into one, so the note stays a fixed size however long the run gets and each call's input is bounded; the summary rides in the note `trim_history` already protects and `_with_note` already rewrites rather than doubles (`running_summary` reads it back off the note's own key). The bracketed count and the way back close BEFORE the summary begins — the first is a harness fact and the second a model's account of turns nobody can see any more, and run together the second would borrow the authority of the first. `trim_history` itself is untouched: the hook summarises only what the deterministic trim already dropped, never what to drop.

**No tool is bound for it, and that is the point of calling it a hook.** The agent did not choose to compact, is not shown that conversation, and compaction is not a move in its protocol — offering it a `submit_summary` would put the agent's own tool-protocol costume on an intervention the harness makes over its head, blurring the one thing this package is most careful about. So the call goes out through `AgenticLLM.call_prose`: no tools, no `response_format`, sharing `_begin`/`_account` with `call_tools` so its tokens cannot leave the cost table. **What changed from v1 is the transport, not the design.** v1 (2026-09-03, removed 2026-09-05) reached the model through `AgenticLLM`'s JSON-mode `__call__` while asking for prose, so a compliant backend answered with a JSON object and the summariser threw it away as non-prose: every compaction on run e81b8108 logged "count only" after a 2.7–4.7k-token completion — three calls, 11.8k completion tokens, nothing kept. `AgenticLLM.__call__` stays gone and `response_format` must never come back on this path; `_clean` now SALVAGES a JSON-wrapped answer with exactly one string value, so the failure that killed v1 is a recovery here. The class invariant is unchanged in force and restated in scope: tool calls are the only way an AGENT reaches the model.

**The stage BRIEF is excluded from the fold.** `compact`'s `restore` already re-attaches a lost contract verbatim and `respec` does the same on any rejection, so a paraphrase is work done twice for a worse copy; at up to 7,400 characters against `MAX_INPUT_CHARS` 12,000 one dropped `implementation` brief would take 62% of the input allowance and push the tool results out through the elision; and a prose paraphrase of a JSON schema sitting in a protected, never-trimmed message is exactly how run 2b9e911a's model came to invent `instructor_guidance` and a dict `session_guides`. A dropped `submit` likewise renders as `[called <name>]` — names, never arguments — so the agent's own committed artifact is not fed back into its own summary.

**The call is the ORCHESTRATOR's**: `ORCHESTRATOR` identity, tokens on the books, and no context published in any agent's name. That is the line between this and the generative repairs removed 2026-09-03, which opened a second conversation under the OWNING AGENT's name — and because none of the three guards in `tests/test_one_agent_one_system_prompt.py` would catch a regression (a two-message conversation slips past the four-message filter), `tests/test_compaction.py` holds it with a guard that `call_prose` has exactly ONE caller in `src/` and that it is the hook. **Failure is always safe**: model error, empty answer, unsalvageable JSON, nothing dropped, no hook at all — every branch falls back to the PREVIOUS summary, never to empty (a failed fold must not erase what earlier ones kept), and the compaction itself always succeeds. `metadata.autonomy` reports `compactions` and `compaction_summaries` per stage, and the difference is the hook's failure rate on this model; `compactions` now ALSO counts the fan-out Developers' compactions, which were never rolled up before, so the existing series is not directly comparable with pre-2026-09-08 runs. The arms pay very differently — `single` carries one conversation all run and reaches compaction far sooner than `multi` — and that is the point: the trigger, the prompt, the budget and the fallback are ONE implementation both call identically, and a cost that differs because of the mechanism is the effect being measured. `tools.tool_menu` is RENDERED FROM `tool_specs` so the two cannot disagree: written by hand it still announced one `submit` after the per-artifact split, so every stage of every arm named a tool that was not bound and `_submit_alias` was silently rescuing it. And a loop's published `_specs` are ACCUMULATED across the conversation (`_merge_specs`), because a binding shrinks — the replan round binds only `submit_dev_plan`, and `react_specs` drops a stage's submit once it is complete — so publishing the live binding alone made a context claim the agent never had the tool it had just used.

**Contexts stream LIVE (2026-09-03).** Each loop republishes its context after every turn (`ToolLoop._publish(live=True)` / `ReactLoop`), so the app's Context tab fills in and its meters move while the agents are still working instead of a row appearing only once its agent has finished. Three things keep it affordable: the per-turn publish is skipped entirely when nobody is watching (`TrajectoryLogger.is_observed` — the emit is a no-op without a consumer but SERIALIZING the transcript to build one is not, and a benchmark run must not pay it); `RunState.add_context` and `Memory.remember_context` UPSERT by the context's `id`, or `result["contexts"]` would be a pile of prefixes of itself — that id is an AGENT RUN id (`core.memory.new_agent_run_id`), minted where the CONVERSATION begins and carried on the loop, so it travels in every snapshot and neither the server nor the browser has to know what a context's identity is made of. **Not derived from what the context is about**: the first version hashed `(agent, phase, label, attempt)`, and the replan round — which continues the Designer's own message list under a new step name — hashed to a different id, so the tab showed that conversation as TWO rows with the second containing the first. Same system prompt in both, so `test_one_agent_one_system_prompt` passed it; the split had simply moved from the prompt to the label, and `test_one_conversation_is_one_context` is the guard for that half. A loop that CONTINUES another's messages inherits everything that describes the CONVERSATION rather than the task — `agent_run_id`, `label`, `compacted`, and `attempt` (the only such caller is `runner._replan_rounds`). `attempt` counts REGENS; numbered from the replan round instead, a perfectly healthy Designer counted as twice-run. It is data, not a label — the tab surfaced it as a "retry #N" badge and that was worse than nothing, since every reader who saw it had to work out whether something had gone wrong, while the rows are already in publication order so one stage's attempts read top to bottom unaided; a regen, a fan-out work set and each arm's design loop all start a fresh message list and so get their own. The transcript export addresses a context by that id (`?context=`) rather than by position, which is only stable once the run is over; **auto-compaction is SHOWN, not counted**: `trim_history` returns the messages it dropped (not a count), the loop accumulates them in `compacted`, and `compacted_transcript` republishes the whole conversation in order with those turns flagged `compacted: true` — dimmed and badged in the tab, and deliberately NOT in the token figures, which measure what is being sent. The dropped run is contiguous and starts right after the system message, which is what lets the order be rebuilt as `[system] + everything dropped so far + what is left` with no positional bookkeeping. Before this, a trimmed transcript answered "what was this agent shown" for the LAST call only and everything earlier was gone but for `history_dropped`, a number saying how much was lost and nothing about what. A loop that continues another's messages inherits its `compacted` too. The SSE frame carries `contexts_light()` — the rows WITHOUT their transcripts, which is the whole of the list view — with the transcripts and the TOOL SCHEMAS fetched per row from `/contexts?context=<id>` when a reader opens one, and re-fetched as that row grows — so a listed row costs almost nothing and the one being looked at is live. (The schemas are half of what the model sees and are excluded from the frame for the same size reason as the transcript; when live rows first landed, the Tool schemas section rendered empty because it was reading a row that by design has none.) `add_context` deliberately does NOT `_notify()`: waking the stream once per turn drained it far ahead of the events.jsonl flusher and turned a rare disk-replay race into a reliable one; the frame rides the next event's wakeup, and `llm_started`/`llm_finished` bracket every model call. That race is also fixed at its root — `_flush_state` now runs BEFORE `state.finish()`, which is what closes the live stream, so nothing is left unflushed when a reader returns.

**Live progress (`on_event`).** `MetaAgent.run` takes an optional keyword-only `on_event(kind, payload)` consumer, wired through `TrajectoryLogger`. It is purely additive — with no consumer every emit is a no-op and the recorded trajectory is byte-for-byte what it was — and exists because the harness is synchronous and one run takes 4–7 minutes, so a UI has nothing to show otherwise. Beyond mirroring the recorded streams it emits `phase_started`/`phase_finished` (from `core/runner.py`) and `llm_started`/`llm_finished` (from `core/agentic/client.py::AgenticLLM`), which record nothing but are the only signal during the ~50 s a single model call takes, plus `graph_snapshot`. A consumer that raises is swallowed; `HarnessCancelled` (a `BaseException`) is the deliberate exception and is how the app stops a run. **A `graph_snapshot` payload must be consumed synchronously** — it aliases the live graph, which later phases keep mutating.

**RAG = external-corpus retrieval only, and it is on-demand.** `use_rag` is off by default and off on the benchmark. When enabled, retrieval is NOT performed upfront: retrieval is a TOOL (`retrieve`) the agent chooses to call and writes the query for, so the pre-agentic separate decision call is subsumed by that choice (`loop.ToolLoop._retrieve` → `core/rag/planner.py::RetrievalPlanner` over `core/rag/agent.py` retrieval agents; `core/rag/sandbox.py` still executes multi-agent plans). The tool is gated exactly like the old path — on the benchmark it is not even offered. Graph-context retrieval (the AlignmentGraph subgraph) is core, always on, and is **not** called RAG.

## The benchmark (`isd-agent-benchmark/`)

`run_benchmark.py` is the orchestrator. Key facts that aren't obvious from the README:

- **Agents run in-process, not as subprocesses.** `_get_agent_runner(agent_id, llm_config)` imports each agent's Python class directly and returns a `run(scenario) -> dict` closure. The CLI interfaces documented in `shared/interfaces/agent_interface.md` exist but the benchmark does not use them. Agent `src/` paths are added to `sys.path` at the top of `run_benchmark.py`.
- **The evaluator IS run as a subprocess** (`isd-evaluator`), with stdout streamed to parse `__EVAL_PROGRESS__` markers.
- Each agent must return `{"addie_output": ..., "trajectory": ..., "metadata": ...}`. Output schemas live in `shared/schemas/*.json`. The metadata saved in `*_trajectory.json` carries uniform `token_usage` + `execution_time_seconds` for every agent. **Token accounting follows the `LLMConfig` object lineage**: `_get_agent_runner` opens one scope per run with `LLMConfig.new_token_scope()`, `copy_with()` re-shares the counter (as it does the credential/endpoint round-robin), and `run_benchmark` reads `resolved_llm_config._token_counter` after the runner returns. `copy_with()` used to hand out a FRESH counter and the runner leaned on that side effect, which silently required agents never to copy the config they were handed — all six baselines copy it in `__init__` to pin model/temperature, so every one of them reported `token_usage` 0 from 2026-08-29 until this was fixed 2026-08-31, while `alignmentgraph-isd` kept real numbers because its own copy sits behind an `if max_tokens is None` guard the uniform max_tokens never trips. `shared/tests/test_token_accounting_reaches_agents.py` constructs all seven agents and asserts each ends up on the run's counter; only `isd-exp report tables`/`report ablation-tables` never read tokens, so no paper number was affected — `isd-exp report facts` was.
- **`shared/llm`** is the single source of LLM configuration. Agents must NOT read provider env vars or instantiate `ChatOpenAI`/`ChatAnthropic` directly — call `create_chat_model(llm_config)` / `llm_config_from_env()`. `LLMConfig.api_spec` is the API *contract* (`openai_compatible`/`anthropic`), distinct from `provider` (a backend preset label). Add providers via config, not agent code.
- `shared/llm/factory.py` also implements the two serving-protection env flags used for the self-hosted ladder (uniform across all agents — fairness): `AGENT_MODEL_MAX_OUTPUT_TOKENS` (ladder value **8192**) and `AGENT_MODEL_STREAMING=1`. The ladder serves **with thinking ON**: vLLM's `--reasoning-parser qwen3` splits the model's thinking into `reasoning_content`, leaving `content` clean for the tool-call/JSON path, and the harness RECORDS that channel in the transcript (see `core/agentic/transcript.py::serialize_messages`) without ever sending it back — a reply that is reasoning and nothing else is charged as the empty turn it is.
- Agent vs. judge models are configured **separately** (`AGENT_MODEL_*` vs `JUDGE_MODEL_*`) to avoid self-preference bias. LLM judge config supports comma-separated lists aligned across names/providers/URLs, with `|` grouping multiple credentials per judge.
- Agent env-quads for the self-hosted Qwen pods (`QWEN{08B,2B,4B,9B}_AGENT_MODEL_*`) live in a **marker-managed block at the end of `.env`**, written by `isd-exp serve sync-agents` (read-only against the RunPod API). Never hand-edit that block.
- Results land in `results/<dataset>_benchmark_<model>_<run_tag>_<ts>/` (e.g. `test_90_benchmark_Qwen3.5-2B_r1_...`) or `results/single_<ts>/` for single scenarios. Both launchers take `RUN_TAGS` (comma/space-separated, run sequentially per slot).

### Evaluator (`evaluator/`)

`isd_evaluator` package. ADDIE rubric scoring: 33 Context-Matrix sub-steps → 13 consolidated items → 5 ADDIE phases (100 pts), plus BFCL-based trajectory scoring; per-scenario `total_score = 0.7·ADDIE + 0.3·Trajectory` (beware: the aggregate CSV "Avg" column is a mean over LLM judges and diverges when a component is missing — always read per-scenario fields). **RQ1 reports its three LLM judge scores side by side, with no composite as headline** (`config.LLM_JUDGE_SCORES`, read by `isd-exp comparison pool`): `addie_median` is the LEAD because ADDIE measures instructional-design content quality — the construct the research question is about — while `trajectory_score` measures process conformance, a different construct, and `total_score`'s 0.7/0.3 weights come from the benchmark rather than from this study. All three get identical statistics (3 failure policies, Holm per score×policy) under `comparisons.by_score[<score>]`; `total_score` is kept in full for comparability with ISD-Agent-Bench's own reporting. No signal is an endpoint — all three appear side by side in the abstract and main tables; do NOT phrase the ADDIE narrative lead as a "chosen endpoint" or "post-hoc decision" (user 2026-08-04); the construct-match rationale carries it. Multiple LLM judges by default (`--single-judge` to disable). Context-aware weighting in `metrics/context_weights.py`. `experiments/src/isd_experiments/alignment/protocol.py` holds the **RQ2 constructive-alignment evaluation protocol**: deterministic, no LLM in measurement, **NO similarity threshold anywhere**, and reported as a **flat panel with NO primary endpoint**, whose members and size are defined once in `ALIGNMENT_SIGNALS` (6 signals as of 2026-08-30 — never restate the count in prose, it goes stale) — calling one signal "primary" is an implicit composite. Two mechanically independent instrument families, each with its own sensitivity axis: **A, textual correspondence** — exactly the three edges of the Biggs triad: `objective_assessment_similarity` (C2), `objective_activity_similarity` (C3), `activity_assessment_similarity` (C4), all continuous mean-max **rectified** cosine, `max(0, cos)` on [0,1] — a scale choice, not a matching cutoff, never describe it as raw cosine. **B, cognitive demand** (`objective_cognitive_congruence`, `porter_mean`, `webb_bloom_consistency` — no similarity involved). **Both families measure the SAME three edges**: `PORTER_PAIRS` is `objective_assessment` / `objective_activity` / `activity_assessment`, so the families differ by instrument and by nothing else. **Removed outright 2026-08-30** (not kept as diagnostics — dead code around a measurement crawls back into tables): `objective_evaluation_similarity`, `assessment_objective_similarity`, the `objectives↔evaluation` Porter pair, `extract_evaluation_texts`, `counts["evaluation"]`, `NON_PANEL_DIAGNOSTICS`, `NON_DIRECTIONAL_SIGNALS`. Evaluation-phase text mirrors no core graph relation, so no signal reads it; note `porter_mean` therefore CHANGED DEFINITION and old `porter_*` numbers are not comparable. **Naming rule**: a signal is named after the operation it computes, because names get read on figure axes and slides where a name that asserts more than the operation does the work only the validity evidence earns — so "alignment" names the protocol and the `aligned(o)` legs but never a metric, and nothing is called "precision" (that implies a retrieval frame needing a threshold this protocol lacks). Collective terms: benchmark judge values = "LLM judge score(s)" — always the full "LLM judge", never a bare "judge", including in compounds ("LLM judge prompts", "LLM judge drift", "the second LLM judge") — and panel values = "alignment signal(s)", never "alignment score(s)"; the set is still the "alignment panel" and Holm within one of them is "within-signal". Per-metric names unchanged. Identifiers and artifact names follow the same rule: `LLM_JUDGE_SCORES` / `ALIGNMENT_SIGNALS`, `pool/llm_judge.py`, `tab_llm_judge_*` / `fig_llm_judge_*` beside `tab_alignment*` / `fig_alignment_*`, and the family keys `llm_judge` / `panel`. Multiplicity is reported twice per size: `p_holm` within one signal (6 comparisons) and `p_holm_panel` over the whole panel×baseline family. **Degenerate input splits two ways (2026-08-30)**: a set the agent never produced (no objectives / items / activities) is an AGENT failure and scores **0.0 + note** on every signal that references it — including the Bloom-derived ones — while a set that exists but carries no Bloom-classifiable text is an INSTRUMENT limit and stays `None`. Collapsing the two let the worst outputs leave the pooled denominator instead of scoring against the agent, and parse-failure rates rise as the model shrinks, so the missingness tracked RQ1's independent variable. `activity_assessment_similarity` (C4) never depends on objectives and is always computed. RQ2 pooling mirrors RQ1's failure policies: the complete-case layer is over *available* outputs, never call it unconditional; `isd-exp score` always records a `missing_outputs` roster and `isd-exp comparison pool` always reads it to add a failure=0 pass — run over a results dir via `isd-exp score`. Instruments are **preset-only**: encoders from `ENCODER_PRESETS` (`--encoder-preset(s)`/`--all-encoders`), Bloom classifiers from `BLOOM_PRESETS` (`--bloom-preset(s)`, `--bloom-checkpoint`); `--all-arms` runs the whole sweep. With no flag it runs the primary configuration `nemotron` + `bertbloom`. The sweep is a **star, not a grid** — each arm deviates from the primary on exactly one axis (5 arms, not 8). The primary Bloom arm `bertbloom` is a single 6-way softmax `bert-base-uncased` head fine-tuned on the EDM2022CLO corpus of Li et al. 2022 — their corpus, not their classifier design: their notebooks yield either six independent binary heads or one multi-label sigmoid head, both of which need an extra decision layer to produce the single level per text the panel requires. Measured on a held-out split it reaches kappa 0.926 vs the lexicon's 0.650, which is why it is primary; the cost, which must be declared, is that its per-case level assignment is no longer traceable to Anderson & Krathwohl and family B is no longer bit-wise deterministic (a discrete argmax, so fp noise can flip a label rather than nudge a number). **It needs a checkpoint on disk** (`isd-exp bloom train`, ~15 min locally), so alignment scoring is no longer zero-setup; a missing checkpoint SKIPS the arm rather than falling back to the lexicon. The `lexicon` arm is the sensitivity axis for family B (3 of the 6 panel signals are Bloom-derived, so without it that family is checked by no axis) and costs no GPU (`--bloom-presets lexicon --embed-cache-only`); the two arms agree at only kappa 0.665, so neither mirrors the other. Each encoder preset also pins its **backend**: only the 8B primary `nemotron` is served (`api`, endpoints from per-slot `<SLOT>_EMBED_BASE_URLS` written by `isd-exp serve sync-embed`, or `--embed-base-urls-for SLOT=...` — deliberately no shared endpoint/model/revision variable); `bgem3`/`granite` run `local` in-process via sentence-transformers (measured on an M4 Pro: ~44 and ~25 min for the ladder's 335k unique texts), `tfidf` is pure Python. So the pod is needed only while the primary arm is scored. Never embed one model on two backends: the cache key is `sha1(model[@revision]+text)` and does not record the backend, so mixing sources is silent. Full metric definitions: `docs/guides/benchmark_guides.md` Appendix A.

## Common commands

**Everything experiment-related goes through `isd-exp`, run from `experiments/`.** The benchmark
is a tool: its own three scripts exist only for running it standalone. Full workflow, including
audits and paper-table generation, is in `docs/guides/benchmark_guides.md`.

`experiments/isd-exp` is a self-locating wrapper: it finds the `.venv` beside it and execs
the CLI there, so nothing needs activating and nothing goes on `PATH`. Run it as `./isd-exp`
from inside `experiments/`. (`pip install -e experiments/` also works and puts a real
`isd-exp` on that environment's PATH.)

**The repo holds exactly two environments**, and they answer two different questions.
`experiments/.venv` runs EVERYTHING experimental: `isd-exp`, and `run_benchmark.py` too,
which is launched as a subprocess under the very same interpreter (`bench.bench_python()`
and `bin/_matrix.sh` resolve to it, both overridable with `ISD_BENCH_PYTHON`). So the
benchmark, the seven agents, `alignmentgraph-isd` and `isd-evaluator` are ten editable
installs in it — no dependency list can name a path in this checkout, so `isd-exp doctor`
reports which are missing and `--fix` installs them. `alignmentgraph-isd/.venv` is the
demo web app's, and is unrelated: the `[server]` extra must never reach the other one.
A machine that only scores and reports needs neither set — `pip install -e ".[dev]"`
alone still carries no inference stack.

`isd-agent-benchmark/` has NO checked-out venv, and that is not a loss of its
independence: `./scripts/1_setup.sh` still builds one on demand, so the submodule stays
standalone-runnable. The one-way dependency rule is about imports, not about environments.

```bash
# One-time
cd experiments
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
./isd-exp help                  # `help <stage> [<sub>]` for anything below
./isd-exp doctor --fix          # checkout, agent installs, .env symlink, Bloom checkpoint

# Data. `scenarios/train` and `scenarios/test` are committed; every DERIVED subset is
# gitignored and reproduced from them with seed 42, so rebuild rather than hunt in git.
cd ../isd-agent-benchmark && ./scripts/2_split_data.sh     # base 95/5 split
cd ../experiments
./isd-exp data split tune-10        # train  -> train_10 (10 of the 30 cells)
./isd-exp data split test-90        # test   -> test_90
./isd-exp data split ablation-30    # test_90 -> test_30, disjoint from train_10

# Serving. `static` needs only a base URL in experiment.toml or .env; `runpod` discovers pods.
./isd-exp serve sync-agents --dry-run
./isd-exp serve sync-embed

# Cheap checks before spending (roadmap phase 2)
./isd-exp tune run                  # cost/budget calibration on train_10

# Freeze, then verify the endpoints (phase 3)
./isd-exp freeze write --tag v1
./isd-exp audit preflight

# The two official experiments (phases 4-5). EXPENSIVE — both confirm first.
./isd-exp comparison run --dry-run  # prints the launch plan, launches nothing
./isd-exp comparison run
./isd-exp ablation run
./isd-exp audit inflight            # every 30-60 min while running
./isd-exp audit postrun

# Offline scoring and pooling — no agent calls, no regeneration
./isd-exp score results/test_90_benchmark_* --all-arms
./isd-exp comparison pool --auto-encoders --auto-bloom
./isd-exp ablation pool

# The manuscript's numbers
./isd-exp report all                # tables -> figures -> facts -> sync, in dependency order
./isd-exp audit artifacts           # FINAL GATE; exit 1 = missing/stale/placeholder/unwired
```

Running a **different ladder or a different host** is an `experiment.toml` edit, not a code
change: add or remove `[[ladder]]` rungs, set `[serving].provider`. Point at an alternative
declaration with `--config` or `ISD_EXPERIMENT_CONFIG`.

Inside `isd-agent-benchmark/`, for running the benchmark alone — `1_setup.sh` builds the
submodule its own `venv/`, which this monorepo does not keep checked out. From here, use
`experiments/.venv/bin/python` instead and skip it:

```bash
./scripts/1_setup.sh                # standalone only: venv + deps + agents + evaluator
python run_benchmark.py --check     # verify all agent modules import cleanly
./scripts/3_run_benchmark_test.sh   # smoke run, 1 scenario
python run_benchmark.py --dataset test_90 --agents baseline,alignmentgraph-isd
```

Default agents: `eduplanner, baseline, react-isd, addie-agent, dick-carey-agent, rpisd-agent`.
**`alignmentgraph-isd` is NOT in the defaults** — add it with `--agents`. The three ablation
arms (`alignmentgraph-isd-single-prose`, `-single-graph`, `-multi-prose`) are likewise
registry-only: the same adapter with the `agent_mode`/`context_mode` kwargs pinned per agent id.
`isd-exp ablation run` selects all four from `experiment.toml`.

Rate-limit presets (`-r conservative|moderate|aggressive|turbo`) set worker counts and
`BENCHMARK_DELAY` together; per-slot override via `<SLOT>_RATE_LIMIT`.

### Tests

Each package is independently installable/testable with pytest (`requires-python >=3.11`). Run
from the package directory. The benchmark's suites have no environment of their own here, so
name `experiments/.venv`'s interpreter (`$EXP` below) rather than a bare `pytest`, which would
resolve to whatever the shell has:

```bash
EXP=<repo>/experiments/.venv/bin/python
cd experiments && python -m pytest tests/                # experiment tests (offline; scipy is a dev-only oracle)
cd alignmentgraph-isd && python -m pytest tests/         # package tests (network-free; fake llm_factory)
cd isd-agent-benchmark/evaluator && $EXP -m pytest tests/  # evaluator tests (asyncio_mode=auto)
cd isd-agent-benchmark/shared && $EXP -m pytest tests/     # shared model/util tests
cd isd-agent-benchmark/agents/<agent> && $EXP -m pytest tests/  # per-agent tests (where present)
python -m pytest tests/test_addie_rubric_parsing.py::<name>    # single test
```

`experiments/tests/` carries four guards worth knowing before editing, because each one
encodes a decision rather than a preference, and all four caught real regressions during the
extraction:

- `test_architecture.py` — the one-way dependency, no vendor names in code, no `rq/tn`
  naming, no `sys.path` surgery, no `parents[N]` outside `paths.py`.
- `test_stats.py` — every hand-rolled statistic checked against scipy to 1e-9. The
  primitives are stdlib-only on purpose (deterministic, no version drift); scipy is the
  oracle that validates that choice rather than a runtime dependency.
- `test_pool_matches_golden.py` / `test_tables_match_golden.py` — the pooled JSON and every
  table reproduced byte-for-byte against output frozen from the scripts they replaced,
  modulo the declared renames. This is what proves no paper number moved.
- `test_run_dir_naming.py` — a regression guard for a real defect: the old run-dir grammar
  pinned `r\d+`, so an ablation run tagged `a1` parsed WRONG rather than failing, folding
  the tag into the model label and silently disabling the reference-drift gauge.

Lint (evaluator uses ruff, line-length 100, `select = E,F,I,N,W`):

```bash
cd isd-agent-benchmark/evaluator && ruff check src/
```

## Conventions

- Much of the benchmark code, docstrings, and CLI help is in **Korean** (the domain is Korean instructional-systems design). Match the surrounding language when editing a file. `docs/` (guide, summary) is Vietnamese/English.
- "Scenario" (benchmark) and "design brief" (`alignmentgraph_isd`) refer to the same input; the only translation point is `_scenario_to_design_brief` in the benchmark's `agents/alignmentgraph-isd` adapter. Prefer the "design brief" vocabulary inside the package.
- Numbers reported in the paper must come from the generated artifacts (`isd-exp report tables` output), never typed by hand.
- **Generated artifacts are English with a decimal point.** Every caption, column header, table footnote, `\newcommand` comment and `stats_*.md` heading in `results/generated/` is English (in-figure text always was); numbers render `87.77`, not `87,77`. `fmt_num()`/`size_display()` in `isd-exp report tables` (and 11's own copies) enforce the decimal mark — do not reintroduce a `.replace(".", "{,}")`. `isd-exp audit artifacts` check I fails RED on Vietnamese letters or a `{,}` decimal in any artifact.
- **Captions state what the table shows and what a cell is** — roughly 100–250 chars. Methodological justification ("why this metric", "how the arms were run") belongs in the methods section, not in a caption.
- **A mean and its SD must come from the same signal**, and since 2026-09-10 that SD is **across SCENARIOS, not across runs**. TN1 generates one deterministic run per cell, so a run-to-run SD has a single value and does not exist. The pooled per-agent dict carries `sd_{addie,traj,total}_across_scenarios`, which the tables print in parentheses and the figures draw as SEM (`sd/sqrt(n)`); `JUDGE_SD_FIELD` in `isd-exp report tables` and `isd-exp report figures` maps each mean to its own. It is descriptive spread, never a precision claim — interval estimates are the bootstrap CIs. `run_to_run_sd_{addie,traj,total}` still exist and are `None` unless a cell has two or more runs (the targeted repeats do); the bare `run_to_run_sd` is Total, kept only because `isd-exp ablation pool` reads it for the A0 drift gauge — never pair it with an ADDIE or Trajectory mean, and never print it without an `isinstance(x, float)` check. `util.json_safe` converts every non-finite float to `null` at the dump, so `pooled_comparison.json` is valid JSON for strict parsers.
- **Any table cell averaged over a partial scenario set must disclose it.** RQ1 tables print `n` per cell with a starred footnote; the RQ2 tables and panel do the same (RQ2's `n` counts scenarios with *at least one* scored run — a weaker condition than RQ1's all-3-runs complete case, so the two are labelled distinctly).
